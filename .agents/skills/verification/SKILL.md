# verification

## 最高优先级禁令

以下规则优先于本技能的其他规则，后续条款不得作为例外：

1. **真实用户环境是系统验收最高优先级**：系统验收必须保持用户实际使用的入口、配置、依赖、数据路径和可见结果。测试便利、环境隔离、兼容安排和风险控制与验收真实性冲突时，验收真实性优先；未经用户明确批准，不得改变实际用户路径或用替代环境缩小验收范围。排障证据不能替代系统验收。
2. **禁止过度锁与并发设计**：没有真实并发入口、共享资源及用户/协议合同，不设计锁、队列、worker、并发池或异步编排。
3. **禁止 smoke/冒烟测试**：服务存活、健康检查、页面可打开或元素存在只能用于环境就绪，不能作为测试或验收证据。
4. **禁止内部防御式编程**：不为理论非法状态增加 optional 分支、默认值、吞错、重复校验、过滤、fallback 或兼容路径；真实 ingress 仅由唯一 owner 处理。
5. **谨慎看待竞态，大部分情况下不可能出现竞态**
6. **不预设边界情况**：没有用户反馈、真实使用证据或既有明确合同，不把想象中的边界情况写成设计、代码、测试或结论；先完成主路径，后续按实际反馈处理。

## 体验闭环验证

- 验证以用户能否顺畅完成完整目标为准，不以改动文件数量或“最小范围”作为通过标准。
- 除成功结果外，必须覆盖加载、空数据、失败、重试/恢复和操作后状态刷新；发现任一入口能点但无法完成闭环，应回 implementation 补齐，而不是降低验收标准。

## 用户体验验收目标

- 验收的首要问题是：目标用户是否比改动前更容易理解界面、更顺畅完成交互、更可靠获得功能结果。UI、交互和功能只有共同改善该结果才算完成。
- 验证关键路径时同时检查下一步是否清楚、操作反馈是否及时、失败是否可理解和恢复、结果是否可确认；不能只因页面能打开、按钮能点击或接口成功就判定通过。
- 发现新增功能、视觉效果或交互步骤没有带来可观察用户收益，或让主路径更复杂时，回到 implementation/architecture-planning 收敛，而不是以“功能已实现”交付。

## 功能闭环验收

- 正常功能验证只运行项目已有的 Playwright 系统测试。最小单位是一个用户目标闭环：从 UI 入口完成必要操作，走真实前端、后端和当前开发数据库，并看到可见结果、状态刷新及该目标需要的失败恢复。
- 只接受 Playwright UI 操作产生的用户可见结果和关键业务状态转移作为验收证据。请求次数、请求体快照、直接 API/SQL、内部变量、私有 state、源码字符串、完整 DOM 形状、mock 和截图基线不能证明功能。
- 不运行或接受 smoke/冒烟测试。服务存活、健康检查、页面可打开或元素存在只可证明环境就绪，不能证明用户目标闭环或作为交付依据。

## 复杂度验收与回流

- 验证发现同一目标依赖隐蔽顺序、多个无语义状态组合、过多局部补丁或难以解释的中间层时，不因最终结果暂时正确而通过；记录为架构风险，回到 `architecture-planning` 审视概念封装、原语/底层动作、模块边界和适用的设计模式。
- 接受的复杂度必须对应不可消除的业务规则或真实外部约束，并能说明 owner、状态语义和用户结果；不得以模式名称、函数数量或额外测试封装替代这项说明。
- 验证锁、队列、worker 或并发行为时，先确认真实 UI 入口、共享资源和用户/协议合同；没有可达并发场景时，判为过度设计并退回 implementation 删除。不得用私有时序、直接 API/SQL 或人工并发脚本证明其合理性。

## 路径口径

- 本技能中的“根目录/当前根目录”指本轮任务开始时探测到的当前工作目录文件夹根目录（`pwd` 对应的工作区根目录），不是该工作目录下某个子项目、子仓库或模块的项目根目录；例如当前工作目录为 `/root/projects` 时，根目录就是 `/root/projects`，不是 `/root/projects/dataops`。

## mailbox 消息生命周期

- `mailbox.md` 只保存当前未解决、需要协商的消息，不是历史日志、任务清单或完成记录。
- 消息对应的冲突、文件占用或协作事项已处理、完成、释放或经用户确认后，立即删除该消息对应内容；不要追加“已处理”“已完成”“已释放”标记，也不要留下空壳。
- 删除只针对已处理消息，其他线程未处理的内容必须原样保留；一条消息混有已处理和未处理内容时，只删已处理部分，保留未决事项。
- 新增消息前先读取当前内容，避免重复创建；继续协作时只维护未决内容，已删除内容不需要恢复为历史记录。

## 功能模块并行

- 集中验证需要并行收集证据时，只按计划中的独立功能模块或纵向业务切片分配；每个验证单元覆盖该模块的真实入口、跨层合同、持久化和用户结果。
- 禁止按前端/后端、性能/安全等测试任务类型分线程后分别只看局部。每个模块由唯一验证者统一执行并汇总其 Playwright 系统测试。
- 跨模块共享链路、公共合同和整阶段回归由一个集成验证 owner 统一收口；有强顺序依赖或共享环境互斥时按依赖顺序执行，不为并行数量牺牲证据一致性。

## 后端声明式验证

- 声明式后端能力通过触发该能力的 Playwright UI 系统路径验证：真实前端和后端联通后，用户可见结果、权限、校验、事务、序列化、拦截、事件或任务声明符合合同。
- 不以源码字符串、`@Decorator` 正则、私有 metadata 读取或完整 discovery mock 链作为运行时证据。AST 只能证明静态依赖/禁用规则，不能证明声明已被容器发现和执行。
- 扩展能力至少覆盖一个成功发现与执行合同，以及技术方案声明的重复、冲突或缺失配置失败语义；按标准 runner 独立过滤时仍成立，并确认失败路径没有遗留实例、订阅、任务或外部资源。
- 验证声明是唯一事实源：删除注解或模块声明后能力应不可达，不能由中央列表、命名约定或 fallback 装配继续生效。

## 链路边界验证

- 验证前先沿 `source -> transport/API/event -> schema/parser -> service/use case -> persistence/state -> consumer` 确认边界可达性、首次 owner 和下游合同；测试矩阵按真实入口和跨层结果组织，不按每层重复覆盖同一非法值。
- 归因先看完整生产链路，而不是局部调用能否接收某值。只有能证明真实入口可达、且现有 owner 未履约的异常才是实现缺陷；测试自行制造的不可达状态应删除或改回真实入口，不以额外防御“修复”。
- 真实边界包括用户/外部协议、历史持久化、插件/第三方、跨信任域和不可信序列化。若上游合同已经拒绝或转换某非法值，不在下游手工注入该值来制造“边界覆盖”，也不把理论构造当作生产缺陷。
- 集中验证应证明唯一 owner 正确拒绝/转换，以及下游正确消费已验证状态；检查 controller/service/store/consumer 是否重复 parse、normalize、validator、interceptor 或同义 fallback。发现重复处理时回 implementation 收敛，不以新增测试掩盖。
- 失败分析必须区分真实生产路径可达的边界缺陷与人为构造的不可达输入；后者删除测试/夹具，而不是新增运行时拦截。新增运行时校验仍须回 implementation 获用户确认。
- 发现以 hash、checksum、fingerprint、内容比对或碰撞处理证明“更安全/更稳”时，验证真实安全、协议、内容寻址或幂等合同是否存在及其 owner；不存在则判为过度防御并回 implementation 删除，不接受以额外测试或重复哈希掩盖。
- 发现内部 optional 分支、默认值、吞错、重复校验、过滤、fallback 或兼容路径时，按防御式编程处理并要求删除；只有真实 ingress 的唯一 owner 可保留必要处理，且必须有用户可见的合同证据。

## 计划大阶段集中验证

- verification 只接收计划文档中已全部实现并通过整阶段 code-review 的大阶段。一次实现动作、一个功能点、一个文件、一个小批次或尚未完成的阶段都不得进入正式测试。
- 一个计划大阶段可以包含多轮 implementation 和多个任务；这些实现过程不分别触发验证。只有阶段完成门禁满足后，才按 architecture-planning 预先定义的矩阵集中运行一次项目 Playwright 系统测试命令。
- 集中测试按依赖和成本排序执行，但属于同一个 verification 阶段，不在每个功能点之间穿插实现和测试，也不把每条命令拆成独立的“实现 -> 评审 -> 测试”循环。
- 发现失败时先完成整轮证据收集并按共同根因分组，再把关联问题整批退回 implementation；修复完整批问题并通过整阶段 code-review 复评后，统一重跑受影响矩阵，不每修一个 case 就重跑。
- 只有为定位已发生的集中测试失败，才可使用最小过滤命令或诊断探针；它用于定位根因，不是新的功能点验收。最终通过证据仍来自整阶段集中矩阵。

## 开发数据库集中验证

- 涉及数据库的集中测试默认直接使用当前可任意修改的开发数据库；不得为单个测试、case 或集中测试批次创建、启动或销毁临时测试库、数据库容器或替代连接。
- 系统测试的业务步骤和断言只能经 Playwright UI 操作完成。数据生命周期必须可追踪、可清理，且不得用直接 SQL、API、SDK、mock 或 `page.route` 绕过真实链路；验证记录须说明数据生命周期和清理结果。
- 只有用户明确要求隔离数据库环境时，才可改用独立数据库，并在验证报告中记录该例外的原因和范围。

## 响应式更新验证

- 验证状态更新时，触发真实用户操作或真实服务端事件，并等待对应的可观察 UI 状态；不得依赖固定 sleep、重复刷新、测试内轮询或直接接口调用获得通过。
- 验证订阅类功能的断线、取消、页面离开和恢复不会造成过期状态、重复呈现或后台持续工作。
- 发现轮询实现时，确认其仅服务于没有推送/回调能力的外部系统，并具备退避、频率/总时限上限、并发保护、取消、停止条件及用户可见状态；否则退回 implementation 改为响应式方案。

## 断线恢复验证

- 对具备原生持久事实源和稳定游标的上游，验证断线后重新连接会从最后确认的原生游标增量恢复已持久化事实，并继续收到新的实时更新；验证恢复路径没有中止或修改上游任务。
- 验证中间层未以事件 buffer、journal、replay 队列、outbox、补偿 watcher 或自动命令重试替代上游恢复。瞬时未持久化 delta/progress 不作为丢失判定，未知命令执行状态也不得因恢复而自动重发。
- 上游无法提供原生恢复合同则判定方案不完整，退回 architecture-planning 明确责任和用户可见结果；不得接受“本地缓存所以可恢复”作为通过证据。

## 移动端验证范围

- 用户未明确要求移动端适配、响应式布局或小屏交互时，只验证需求指定的目标平台和当前桌面目标视口；不新增移动端视口、断点、触摸交互或小屏兼容测试。
- 只有用户明确提出移动端或响应式范围时，才把对应小屏布局、交互和视觉合同加入验证矩阵与报告；未提出时不得以缺少移动端验证判定不通过。

## 原型 HTML 对比验证

- 验证 UI 复现原型 HTML 时，先让原型和目标 UI 使用同一份或字节等价的 mock 数据快照，并固定数据版本、视口和交互状态；记录 fixture/data contract 的身份作为视觉证据的一部分。
- 数据值、字段类型、顺序、空值/缺失值、筛选、排序、分页或时间状态不一致时，结果必须标记为“不可比”，不得判定 UI 100% 一致，也不得把数据差异当作 CSS/布局失败；先回到 architecture-planning/implementation 对齐数据后再比较。

## 异常可观测性硬门禁

- 验证每条异常路径都在前端或后端产生完整堆栈日志，包括显式 `catch`、重抛/转换、降级返回、全局错误边界、Promise rejection、浏览器 `pageerror`/`unhandledrejection`。
- 日志证据必须包含原始 `name`、`message`、`stack` 和可关联的 request/trace 上下文；只看到错误文案、错误码或 message 不能作为通过证据。
- 脱敏验证必须确认敏感字段被移除而完整堆栈仍保留；异常对象确无 stack 时，记录原始异常表示和运行时限制，不得静默替换为空值。

## 关键函数注释验证门禁

- 验证报告须检查本轮新增或修改的关键函数是否有必要的中文备注，至少能说明函数作用；涉及规则、状态、I/O、异常、并发/事务或复杂算法时，备注还应覆盖关键边界和副作用。
- 只检查备注存在不算通过：备注必须与实现语义一致，不能是函数名重复、逐行翻译或空泛模板；简单 getter/setter 和显而易见的转发函数可排除。

## 反模式

1. 禁止未经测试即交付
2. 禁止以"理论可行"交付——改动必须通过实际运行验证
3. 禁止 API 变更仅靠 mock 或直接 HTTP 验证——正常功能必须由 Playwright UI 驱动真实前后端
4. 禁止前端可见文案未确认 i18n 即交付
5. 禁止排障只留结论不留轨迹——二分/分段/逐层排除须逐点留记录
6. 禁止纯视觉 UI 修改盲跑其他层级或完全不验证——正常功能仍只做目标页面的 Playwright UI 系统测试与 console/network 健康检查；不得加入视觉 baseline 或小屏检查，除非用户明确要求专项范围
7. 禁止重复编写稳定技术步骤，也禁止无门槛抽测试 helper——至少两个独立稳定合同重复的环境、认证、隔离数据、清理、协议模拟、诊断采集和通用技术断言才进入共享层；业务步骤和断言留在测试，无第二消费者或只转发的 helper 必须内联或删除
8. 禁止用新增运行时校验掩盖验证失败——发现确需增加校验时，必须回到 implementation 前请求用户确认；过多运行时校验会增加热路径开销，不能作为默认修复手段
9. 禁止把 plugin 额外字段当作失败条件——插件只需提供必要字段；验证时不得要求字段集合完全相等，不得因未知额外字段判失败
10. 禁止通过新增拷贝逻辑让测试“看起来稳定”——拷贝不能作为默认修复手段；涉及拷贝时必须验证必要性、数据规模、触发频率和热路径性能风险
11. 禁止因薄 adapter 增加测试面——验证失败时不要通过新增 wrapper/mapper/facade 隔离问题；adapter 若只透传或同形映射，应回到 implementation 删除或合并
12. 禁止用测试或运行时拦截替代数据流治理——性能、状态或一致性问题应验证架构是否避免冗余流动和全量处理，而不是通过新增断言、校验、字段过滤或测试夹具硬性掩盖
13. 禁止用测试固化形式主义转换——不要为同形 DTO/VO/Entity/ViewModel/State/Event 转换新增快照或字段逐项测试；若转换没有真实语义差异，应回到 implementation 删除
14. 禁止用近似断言掩盖字段缺失——测试不能只证明“组合字段得到相似效果”；必须验证功能所需语义字段从真实上游数据/API/事件/fixture 传到下游消费点
15. 禁止用非 `NormalizedAgentEvent` 事实源验收 DataOps AI 语义行为——AI runtime/read-model/工具结果/任务/统计/回放测试必须验证语义来自 `NormalizedAgentEvent` 显式字段，不得用 raw payload、metadata、activity title/status、session.jsonl、相邻消息、消息顺序或旧字段 fallback 断言通过
16. 禁止用组件链测试固化前端状态 drilling——Vue 跨多组件状态验证应面向 Pinia store 或 provide/inject 上下文，以及真实消费组件；React 跨多组件状态验证应面向 Zustand store 和真实消费组件；不要为了层层转发的中间组件写脆弱测试
17. 禁止为重构保留旧行为兼容测试——验证只面向重构后的目标合同；旧路径、兼容桥、fallback、双写过渡和旧 fixture 必须删除，不得以“回归保护”名义继续固化
18. 禁止按功能点、实现动作、文件或小批次反复进入验证——只有计划中的整个大阶段全部实现并通过整阶段 code-review 后，才集中运行测试矩阵；失败按共同根因整批退回，修复和复评完成后再统一重跑
19. 禁止测试通过后清除困难排障新增的调试/诊断日志——这些日志是后续定位问题的可维护性代码；验证只要求日志有稳定标签、合适级别、关键上下文、敏感信息规避和热路径门控，不以“测试已过”为理由要求删除
20. 禁止用 fallback 让验证通过——测试不得通过兜底、降级、回退、备用路径或默认替代数据掩盖主路径失败；只有用户明确要求 fallback 时才验证 fallback 行为，否则发现 fallback 必须回到 implementation 删除并修正主路径
21. 禁止系统测试每次都从零逐步操作——验证必须先查项目 Playwright 命令和 UI 测试 SDK；重复的登录、导航、等待、控制台采集和通用断言不得每次手写。手工浏览器步骤只用于探索或定位假设，不能替代可复用系统测试
22. 禁止为了验证通过而撤回或修改其他线程改动——验证发现失败、快照差异或工作树变化时，不得直接清理、回滚、重写疑似其他线程改动；先在当前工作目录文件夹根目录 `mailbox.md` 协商，转向无冲突验证项，达成一致或收到用户指示后再处理冲突文件；处理完成后立即删除对应消息，不写完成标记
23. 禁止浏览器端到端测试只看页面结果——Browser/Playwright/Cypress 验证必须同时检查控制台和网络请求；不得忽略相关 console error/warn、request failed、意外 4xx/5xx、CORS、静态资源/API 失败、长时间 pending/stalled 请求。已知第三方噪声必须说明来源和为何不影响目标流
24. 禁止用测试通过掩盖实现过复杂——验证阶段除功能正确外，还要确认本轮没有让心智模型和数据流明显变复杂；若同一需求存在更简单实现，不能只因复杂方案测试通过就交付
25. 禁止用测试或校验接受对象同义冗余字段——验证阶段要确认本轮新增/修改的对象、payload、state、event、DTO、fixture、mock、配置没有意义完全相同的冗余字段；不得通过新增运行时校验、快照白名单或测试适配来接受双字段并存
26. 禁止交付包含思维链或隐藏推理的产物——验证 HTML、Markdown、PDF/报告、页面文案、注释、fixture、snapshot、debug 面板、内嵌 JSON、脚本变量、日志和测试输出时，发现 chain-of-thought、scratchpad、内部推理、思考过程、提示词片段、系统/开发者指令或模型分析过程即验证失败；必须回到 implementation 从生成源头删除或改写为结论、决策、假设、证据和必要理由，不得靠运行时扫描、过滤或校验通过
27. 禁止把脚本能运行当作测试有效——源码字符串、正则、标识符、函数顺序、模板片段、mock 调用和局部 CSS 文本不能证明运行时行为；正常功能只接受 Playwright UI 系统测试证据
28. 禁止临时发明永久测试补报告——verification 只执行既定矩阵；发现覆盖缺口时回到 architecture-planning/implementation 决定层级、复用、改造和入口
29. 禁止接受白盒、mock 自证或孤儿测试——私有访问、完整内部 mock 链、未进入标准 runner 的测试即验证不通过
30. 禁止把 mock 浏览器用例称为系统测试——route mock、直接 API/SQL 或替代后端链路均不属于系统测试；系统测试必须驱动真实目标链
31. 禁止把截图文件当作系统测试通过——截图只能作为人工证据
32. 禁止把脚本退出码和 `[PASS]` 日志当成现代测试证据——永久测试须由项目已锁定的现代 runner 或语言标准 runner 报告独立 case/suite、失败名称、耗时与退出状态；须能按 case 过滤，并由 runner hook/fixture 证明失败路径 cleanup。顶层 assert、`main().catch()`、逐文件子进程和把整份旧脚本包成唯一 case 均验证不通过
33. 禁止接受异步注册或兄弟依赖的 case——suite/test 必须同步注册，setup/cleanup 使用 runner hook/fixture；不得在 async suite callback 中执行环境准备后 `await test(...)`，不得让 case 依赖兄弟 case 的执行、创建数据、共享变量修改或顺序。按名称只运行目标 case 时仍须通过其自身合同；不可拆的连续原子事务应合并为一个 case
34. 禁止把不可达非法值当作边界验收——测试必须证明真实 ingress boundary、唯一 owner 和下游消费合同；上游不可能产生的值不得在下游重复注入、拦截或永久测试

## 测试 SDK

通用测试步骤沉淀为项目级测试 SDK，新测试优先复用：

- **已有 SDK 则复用**——先查项目中是否已有 test-utils / test-helpers / fixtures / test-sdk 等测试基础设施
- **稳定重复后再建**——首次且尚未稳定的业务流程留在测试内；登录、数据准备/清理、诊断采集等技术步骤确认稳定重复后再抽成 SDK
- **系统测试先走项目入口**——先查 `package.json` Playwright 脚本、`playwright.config.*`、系统测试目录、fixture 与 page object；有既有入口时优先运行或扩展它，不改用其他 runner
- **系统测试必查控制台和网络**——项目 Playwright helper 或临时探索都要采集 console error/warn、requestfailed、意外 `4xx/5xx`、CORS、资源/API 失败和目标交互后的关键请求结果
- **临时浏览器脚本只作探索**——临时 Playwright/Browser 操作可用于定位、截图、console/network 取证和视觉检查；一旦该流程需要回归保护，必须沉淀为项目测试或测试 SDK，不得把临时脚本当最终验证
- **SDK 职责**：Playwright 环境准备/清理、通用 UI fixture、console/network 采集、服务复用与认证辅助；不得提供 mock/stub、直接 API/SQL 或业务断言
- **SDK 不含业务逻辑**——业务特定的断言和数据留在测试文件里，SDK 只管"怎么搭台子"，不管"台上演什么"
- **抽取门槛**——共享能力必须有至少两个当前独立稳定消费者，输入输出、owner、setup/cleanup 生命周期和失败清理明确；禁止为未来可能复用预建
- **唯一入口**——同一能力只保留一个权威实现，消费者直接导入；禁止 barrel/re-export、兼容路径、同形 wrapper 和重复 SDK
- **退役检查**——消费者只剩一个、runner 已原生提供、合同已经分化或共享层出现业务分支时，验证不通过，须回到 implementation 内联、拆回 owner 或删除

## 验证类型

正常功能只有一种正式验证：Playwright UI 系统测试。它通过真实浏览器驱动真实前端、后端和开发数据库，以可见结果、刷新后的状态、失败恢复及 console/network 健康作为证据。不得增加或运行其他测试层级。

下列历史层级说明不适用于正常功能验收；除用户明确要求专项测试外，不得据此增加或运行对应命令。

- **static**：typecheck、lint、AST、结构化配置与依赖边界；不证明运行时行为。
- **unit**：纯函数、算法、局部状态转移。
- **component**：真实渲染、交互、store/context 与消费组件。
- **contract**：HTTP/event/schema 序列化、解析、状态码与错误语义。
- **integration**：多模块、数据库、队列、浏览器与模拟外部系统。
- **e2e**：真实前后端、授权数据源和用户路径。
- **visual**：baseline 或明确响应式、溢出、重叠、可访问性合同。
- **performance**：固定数据集下的热路径、时延和资源上限。

优先覆盖稳定合同和高风险路径，不追求测试数量或覆盖率数字。一个验收标准可由多个层级共同证明，一个测试也可覆盖同一业务结果下的多个实现细节。

## 产出

- 测试报告：每条验收标准的通过/不通过 + 证据（命令输出、截图、日志片段）；若通过调试/诊断日志定位或证明问题，记录相关日志标签、触发条件和关键片段，并确认日志代码已保留
- 测试治理报告：记录稳定合同、Playwright 系统测试入口、真实前后端边界、开发数据库生命周期、复用/删除的旧测试，以及源码字符串、白盒、mock、自建 API/SQL、孤儿测试和截图即断言的审查结果
- Runner 现代化报告：记录 runner 来源及 package/lockfile 归属、原生 case/suite 数量、同步注册、hook/timeout/mock/隔离/reporter 使用、按 case 独立过滤证据，以及删除的顶层断言、main 脚本、自建逐文件执行、async suite/兄弟依赖和形式主义包装
- 测试复用报告：逐项记录共享能力 owner、直接消费者、抽取依据、承担/不承担职责、setup/cleanup 证据、唯一导入路径和退役条件；确认没有把业务断言、源码正则、巨型默认 fixture 或薄 adapter 包装成复用
- 运行时校验审查：确认本轮未引入未经用户确认的运行时校验；若有已确认校验，记录位置、触发频率和性能影响
- 链路边界审查：记录真实边界来源、source-to-consumer 链路、唯一校验/解析/拦截 owner、上游合同和下游不重复处理假设；确认没有为不可达非法值新增测试、夹具或运行时拦截
- Plugin 字段兼容审查：涉及 plugin 模式时，验证必要字段存在即可通过，并覆盖携带额外字段时不被拒绝的场景
- 拷贝逻辑审查：确认本轮未引入非必要拷贝；若有必要拷贝，记录拷贝对象、数据规模、触发频率和热路径影响
- Adapter 审查：确认本轮未引入薄 adapter；若保留 adapter，记录真实适配职责和无法直接调用的原因
- 数据流审查：确认本轮没有不合理冗余数据流动、无必要全量处理、重复 normalize 或过大事件载荷；若保留全量处理，记录必要性、数据规模、触发频率和替代方案
- 转换逻辑审查：确认本轮没有为了转换而转换；若保留转换，记录源模型、目标模型、真实差异和不可删除原因
- 字段衔接审查：确认功能所需语义字段已从源头传到消费点；若新增字段，记录字段来源、经过的合同/API/事件/类型/fixture 和覆盖测试；确认未用其他字段组合近似替代
- DataOps AI 事实源审查：涉及 AI runtime/read-model/工具结果/任务/统计/回放时，确认语义事实只来自 `NormalizedAgentEvent` 显式字段；确认没有 raw payload、metadata、session.jsonl、相邻消息、消息顺序或旧字段 fallback
- 前端状态流审查：涉及 Vue 跨多组件状态时，确认使用 Pinia 或 provide/inject 管理；涉及 React 跨多组件状态时，确认使用 Zustand 管理；确认没有新增 props/emit/ref 或 props/callback/state 层层转发，并覆盖 store/context 与真实消费组件的交互
- 重构收敛审查：确认旧路径、旧字段、旧测试、兼容层、fallback、双写和临时开关已删除；所有验证只覆盖目标新合同
- 大阶段集中测试审查：确认测试对应计划中哪个大阶段，该阶段全部任务和整阶段 code-review 已完成后才统一执行；记录 Playwright 系统测试命令、失败分组和整批修复后的重跑结果，确认未按功能点往返测试
- 开发数据库验证记录：确认数据库测试复用当前开发数据库，记录测试数据的创建、迁移、修改和清理结果；确认未为单个测试、case 或测试批次创建、启动或销毁临时测试库
- 诊断日志审查：遇到难以排除的问题时，确认已增加并保留有信号的调试/诊断日志；检查日志级别、稳定标签、关键上下文、敏感信息规避和热路径性能影响
- Fallback 审查：确认本轮未新增用户未明确要求的 fallback、兜底、降级、回退、备用路径或默认替代数据；若用户要求 fallback，记录用户要求、触发条件、主路径失败证据、状态收敛和数据流复杂度影响
- 测试 SDK 审查：涉及浏览器/e2e 验证时，记录复用的项目 e2e 命令、test helper、fixture、page object 或新增的 SDK 位置；若只做临时浏览器探索，说明为什么不需要回归测试沉淀
- 并发协作审查：确认验证过程中未撤回、覆盖或顺手修改其他线程改动；如发现冲突文件，记录当前未决的 `mailbox.md` 协商信息、已转做的无冲突验证项和恢复处理条件；协作处理完成后确认对应消息已删除
- 浏览器端到端健康审查：涉及 Browser/Playwright/Cypress 时，记录控制台检查结果和网络请求检查结果；列出相关 console error/warn、失败请求、意外 4xx/5xx、CORS、资源/API 失败、pending/stalled 请求，或说明无相关异常
- 简单性审查：确认本轮实现的心智模型和数据流足够简单；记录是否存在更简单实现，若保留复杂方案，说明复杂度必要性和不能简化的原因
- 对象字段唯一性审查：确认本轮没有新增意义完全相同的对象冗余字段；若做字段收敛，记录唯一权威字段、删除的同义字段，以及类型、调用方、fixture、mock、测试和文档的同步结果
- 产物泄露审查：确认本轮生成或修改的 HTML、Markdown、报告、页面文案、注释、fixture、snapshot、debug 面板、内嵌数据、日志和测试输出不包含思维链、隐藏推理、scratchpad、提示词片段、系统/开发者指令或模型分析过程；若需要解释，只保留结论、决策、假设、证据和必要理由
- 全部通过 → 可交付
- 有不通过 → 回到 implementation，附失败证据与定位轨迹
