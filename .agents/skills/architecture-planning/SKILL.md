# architecture-planning

## 最高优先级禁令

以下规则优先于本技能的其他规则，后续条款不得作为例外：

1. **禁止过度锁与并发设计**：没有真实并发入口、共享资源及用户/协议合同，不设计锁、队列、worker、并发池或异步编排。
2. **禁止 smoke/冒烟测试**：服务存活、健康检查、页面可打开或元素存在只能用于环境就绪，不能作为测试或验收证据。
3. **禁止内部防御式编程**：不为理论非法状态增加 optional 分支、默认值、吞错、重复校验、过滤、fallback 或兼容路径；真实 ingress 仅由唯一 owner 处理。
4. **谨慎看待竞态，大部分情况下不可能出现竞态**
5. **不预设边界情况**：没有用户反馈、真实使用证据或既有明确合同，不把想象中的边界情况写成设计、代码、测试或结论；先完成主路径，后续按实际反馈处理。

## 体验完整性与最小必要复杂度

- 架构方案追求顺畅、可理解的用户心智流和完整业务闭环；“最小改动”不是独立目标，也不能成为拒绝必要跨模块变更的理由。
- 先确定用户从入口到结果、失败恢复和后续维护的完整路径，再选择能覆盖该路径的最少模块、状态和数据转换。需要同步 API、前端、原型、持久化、权限、审计或测试时，应在同一阶段一次收敛。
- 评审时同时检查“是否能做”和“用户是否能顺利做完”；技术上可用但操作不可发现、错误不可恢复或状态语义混乱的方案不通过。

## 体验驱动的技术决策

- 架构的最终目标是改善用户完成任务的体验。模块、数据流、UI 结构、交互状态和功能边界都必须服务于更易理解、更少阻塞、更可靠完成的用户路径。
- 方案必须把每项关键 UI、交互和功能变化映射到用户阻碍、预期体验改善和可观察结果；不能说明用户收益的抽象、状态、接口或页面复杂度应删除。
- 在技术性能、视觉效果、交互丰富度与功能范围发生取舍时，优先保护用户主路径的可发现性、响应性、可恢复性和结果确定性。

## 局部复杂度回溯

- 把嵌套分支、难以命名的 helper、调用方编排多个底层步骤、分散状态写入、参数组合爆炸或重复转换视为架构审查触发器；先查复杂度根源，不以继续拆函数、加 flag 或补 wrapper 结案。
- 重新检查业务概念、模块边界和数据所有权：让概念拥有自身不变量、状态转换和语义动作；将原语和底层动作收敛为可组合、可命名且对应稳定领域意图的最小操作，避免 UI/调用方了解内部顺序或半成品状态。
- 只在能隔离明确变化轴、生命周期、状态机或外部协议差异时采用适合的设计模式；若直接流程、清晰概念或更少模块已足够，禁止为了模式再引入抽象层。

## 路径口径

- 本技能中的“根目录/当前根目录”指本轮任务开始时探测到的当前工作目录文件夹根目录（`pwd` 对应的工作区根目录），不是该工作目录下某个子项目、子仓库或模块的项目根目录；例如当前工作目录为 `/root/projects` 时，根目录就是 `/root/projects`，不是 `/root/projects/dataops`。

## mailbox 消息生命周期

- `mailbox.md` 只保存当前未解决、需要协商的消息，不是历史日志、任务清单或完成记录。
- 消息对应的冲突、文件占用或协作事项已处理、完成、释放或经用户确认后，立即删除该消息对应内容；不要追加“已处理”“已完成”“已释放”标记，也不要留下空壳。
- 删除只针对已处理消息，其他线程未处理的内容必须原样保留；一条消息混有已处理和未处理内容时，只删已处理部分，保留未决事项。
- 新增消息前先读取当前内容，避免重复创建；继续协作时只维护未决内容，已删除内容不需要恢复为历史记录。

## 功能模块并行

- 并行单元必须是可独立开发、集成和验收的功能模块或纵向业务切片，不是产品设计、架构、编码、评审、测试、文档等任务类型。
- 每个并行模块应包含实现该能力所需的生产代码、接口/类型、调用方、迁移、测试代码和文档，并有单一模块 owner；同一模块不得按任务类型交给多个线程来回交接。
- 只有模块边界、输入输出合同、文件归属、依赖顺序和集成点明确，且并行后能减少关键路径时才并行。共享合同或共享基础设施先由唯一 owner 收敛；存在强顺序依赖或大量共享文件时改为串行。
- 技术方案必须输出功能模块并行图：模块目标、owner、文件范围、上下游合同、前置依赖、合并顺序和整阶段集成点。禁止按“后端线程/前端线程/测试线程/评审线程”分类制造表面并行。

## 运行时并发与锁最小化

- 区分开发协作并行与运行时并发；默认保持一个用户动作内的顺序数据流。只有真实并发来源、共享资源、吞吐/时延目标或外部协议明确要求时，才设计并发、队列、worker、任务调度或锁。
- 先通过数据所有权、单写者、资源分区、不可变数据、顺序编排及框架/数据库已有事务语义消除竞争；不得为理论 race condition 预建 mutex、semaphore、全局锁、多锁顺序、并发池或自定义调度器。
- 并发确有必要时，方案必须写清触发源、共享资源、唯一 owner、原子性/顺序/隔离语义、并发上限、取消/超时/资源释放和用户可见结果。锁只能覆盖最小临界区，不能替代边界设计或掩盖状态所有权不清。

## 后端声明式开发

- 后端优先用框架原生声明式能力表达稳定机制：注解/装饰器、模块 metadata、DI provider、schema、路由、权限、校验、事务、序列化、拦截器、事件订阅和任务调度。不得用散落命令式 wiring、中央 `switch`、手工 registry、文件名约定或源码扫描维护同一事实。
- 扩展功能默认采用注解驱动：实现公开 provider/interface 合同，标注框架可发现的注解/装饰器，并纳入所属模块的 DI/discovery 范围。新增扩展应主要增加自身实现与声明，不要求修改无关中央分发表。
- 方案必须定义声明的目标、参数合同、发现范围、优先级/冲突规则、实例作用域、启动失败语义和可观察验证方式。声明是权威配置，不与另一套命令式注册或兼容列表双写。
- 声明式只负责装配、策略和跨切面元数据；领域算法、状态转移和有序业务流程仍放在显式 service/handler/use case 中。不得把复杂控制流、隐藏 I/O、fallback 或业务分支塞进装饰器工厂、schema hook 或自造 DSL。
- NestJS 优先复用 `@Module`、`@Injectable`、`@Controller`、guards、pipes、interceptors、filters、custom metadata、DiscoveryService 和 DI scope。只有原生机制无法表达且方案说明必要性、启动成本和替代方案时，才设计自定义扫描/注册基础设施。

## 链路边界与单一校验 Owner

- 任何边界判断都必须沿完整链路分析：`source -> transport/API/event -> schema/parser -> service/use case -> persistence/state -> consumer`。先说明值从哪里来、经过哪些合同、在哪一层首次可被接收/转换/产生，再决定是否需要校验、解析、归一化或拦截。
- 先以“是否从真实 source 经既有合同可达”判断问题是否存在。不可达的局部理论状态不是系统需求、风险或测试目标；不得为了局部稳健性引入全局重复分支、类型扩张、状态分叉或热路径成本。
- 真实边界包括用户输入、外部 HTTP/event、数据库历史数据、插件/第三方协议、跨信任域传输和不可信序列化。若上游类型、schema、解析器或框架装配已经保证某个非法值不可达，下游不得仅因“理论上可以构造”把它当作本层边界。
- 每个可达边界条件必须明确唯一 owner、输入/输出合同、失败语义和下游假设。禁止对同一非法值重复 schema parse、normalize、validator、interceptor、权限/状态拦截或同义 fallback；不同层只有在处理不同真实边界时才可分别存在逻辑。
- 方案必须列出下游依赖的已验证状态/最小字段，以及为什么下游不再重复处理。发生绕过上游 owner 的真实入口时，应把校验放在该入口，而不是在所有消费层复制防御。
- 新增运行时校验、fallback 或拦截器前，必须写清非法值的真实来源、首次拥有边界的层、已有 owner 为什么不能承担、触发频率/热路径成本和不会造成重复处理或数据流分叉的理由；未经用户确认不得新增。
- 哈希、校验和、指纹、内容比对和碰撞防护不是默认架构策略；不得仅为理论篡改、重复、误传或碰撞风险在内部链路增加它们。只有密码/签名/完整性、外部协议、内容寻址或幂等去重等真实合同需要时，才指定唯一 owner、威胁来源、算法/载荷、性能成本和替代方案。
- 禁止把防御式编程作为内部架构策略：不得因“万一非法”在每层添加 `undefined` 分支、默认值、吞错、重复校验、过滤、fallback 或兼容路径。真实 ingress 只在唯一 owner 校验，其他层依赖合同并让合同破坏可定位。

## 大阶段与集中测试

- 技术方案必须先划分“大阶段”：一个阶段应形成可整体评审、可集中验收的完整业务或架构能力，包含相关生产代码、类型、调用方、迁移、fixture、测试代码和文档；不得按单个按钮、接口、函数、文件或零散功能点切成测试批次。
- 每个大阶段只设置一个集中测试门禁。该阶段全部功能点实现完成、旧路径清理完成、代码评审复评通过后，才从 implementation/code-review 进入 verification，按测试矩阵集中运行。
- 正常功能开发的测试矩阵固定为系统测试一层：仅使用项目已有的 Playwright，从 UI 操作驱动真实前端、后端和当前开发数据库。不得为同一阶段规划 unit、component、contract、API 直调、mock、visual 或 performance 测试。
- 不得规划、运行或保留 smoke/冒烟测试；页面可打开、进程存活或健康检查只可作为环境就绪条件，不能进入测试矩阵或证明功能通过。
- 任务清单不得在每个功能点后插入“运行测试”。实现阶段可以同步编写和自查测试代码，但不进入正式 code-review、不执行阶段验收命令，不因小改动反复启动 runner、浏览器、数据库或服务。
- 实现被阻塞且必须验证根因假设时，只允许一次最小诊断命令或探针；它不算测试阶段、不作为通过证据。定位后继续完成整个大阶段，最终仍由 verification 集中执行完整矩阵。
- 大阶段必须有明确完成条件和测试矩阵；若范围大到无法一次评审和验收，应在架构阶段按可交付合同重新划阶段，而不是退化为每个功能点都测试。

## 响应式状态更新

- 状态更新优先沿真实变化链路传播：用户操作的响应、后端事件、WebSocket/SSE/订阅或受控 store 状态更新；不得为方便实现新增定时刷新、递归请求或多处重复拉取。
- 技术方案必须明确状态 owner、事件源、订阅生命周期、失效/断开处理和 UI 更新路径，避免消息丢失、重复消费或页面卸载后继续工作。
- 只有外部系统无法推送且无回调能力时才可使用轮询。方案须记录该事实、退避策略、频率上限、总时限、取消/卸载清理、错误呈现和何时停止；固定间隔无限轮询不通过。

## 断线恢复的原生事实源

- 为每条会断开的上游链路先确认权威持久事实源、稳定原生游标和上游定义的增量读取/订阅衔接合同。三者齐备时，唯一恢复路径是重新连接 -> 从最后确认的原生游标增量读取 -> 在适配边界投影 -> 继续实时订阅；游标只是恢复位置，不能演化成第二份会话事实或事件日志。
- 禁止因传输断开新增 DataOps 事件缓冲、runtime journal、replay 队列、outbox、补偿 watcher、连接压力熔断或自动命令重试。瞬时且未持久化的 delta/progress 不属于恢复事实；未知命令是否已被上游执行时不得自动重发。
- 若上游不能提供持久事实源、稳定游标或无缺口衔接合同，先停止方案并明确恢复、重复命令和用户可见状态的协议责任；不得默认用本地队列填补该缺口。

## 系统测试合同设计

- 系统测试矩阵按用户目标设计，一个 Playwright case 覆盖从 UI 入口到可见结果、状态刷新和必要失败恢复的完整闭环；不要按按钮、HTTP 请求、字段、DOM 节点或实现函数机械拆 case。
- case 的业务步骤和断言只能通过 Playwright 页面操作完成。必须走真实前端、后端和开发数据库；禁止 `page.route`、直接 HTTP/API/SQL、mock/stub、源码断言和截图基线作为正常功能验收。

## 开发数据库测试环境

- 涉及数据库的测试矩阵必须明确复用当前可任意修改的开发数据库；不得为单个测试、单个 case 或每个集中测试批次规划创建、启动或销毁临时测试库。
- 方案须列出测试数据的创建/迁移、修改、可辨识范围和清理恢复责任，复用项目现有的 runner、fixture 或 support 生命周期；测试隔离依靠数据生命周期，不依靠反复切换数据库实例。
- 只有用户明确要求隔离数据库环境时，才可在技术方案中提出例外，并写明原因、范围和生命周期。

## 移动端范围门禁

- 用户未明确要求移动端适配、响应式布局或小屏交互时，技术方案不得规划移动端页面、断点、触摸交互、移动端专属组件或移动端视口测试；默认以当前桌面目标视口完成设计。
- 只有用户明确提出移动端或响应式范围时，才在模块边界、设计系统、测试矩阵和完成条件中加入对应的小屏合同与视口；不得以“完整性”自行扩展范围。

## 原型 HTML 数据合同

- 规划 UI 复现原型 HTML 时，必须把原型 mock 数据的来源、版本、字段类型和值、顺序、空值/缺失值以及筛选、排序、分页和时间状态定义为比较合同，并指定唯一 fixture owner。
- 原型和目标 UI 必须消费同一份或字节等价的 mock 数据快照；不得用另一份近似数据、随机数据或改变语义的 mapper 代替。数据不一致时，测试矩阵只能标记“不可比”，不得产出 100% UI 一致结论。
- 测试矩阵还须固定比较视口和交互状态；只有数据、视口和状态都对齐后，视觉差异才归因于 UI 实现并进入 verification。

## 异常可观测性设计门禁

- 技术方案必须为每条异常处理路径指定前端或后端的日志归属：显式 `catch`、重抛/转换、降级、错误响应、全局边界和异步 rejection 均不得丢失完整原始堆栈。
- 方案须明确 logger/telemetry、级别、request/trace 关联和脱敏边界；脱敏只能作用于敏感上下文，不得截断或覆盖 `name`、`message`、`stack`。

## 关键函数注释设计门禁

- 技术方案必须识别关键函数（跨模块入口、核心业务规则、状态转换、外部 I/O、异常边界、并发/事务协调、复杂算法）并要求在实现中添加必要的中文备注，说明函数作用、关键前置/后置条件和重要副作用。
- 注释应解释“为什么这样做”和边界约束，不重复函数名、参数名或逐行翻译代码；简单 getter/setter、显而易见的转发函数不强行添加注释。

## 反模式

1. 禁止无计划即动手——必须先产出技术方案与任务清单
2. 禁止无完成条件与验证方式即进入实现
3. 禁止为低频低影响特例引复杂入主干
4. 禁止新增抽象不降低真实复杂度
5. 禁止同义字段多套并存——同一对象、payload、state、event、DTO 或配置里不得出现意义完全相同的冗余字段；应在字段合同中选定唯一语义字段并同步生产者、消费者、类型、fixture 和文档，不能用运行时校验、字段白名单或兼容映射来掩盖字段设计不清
6. 禁止跨模块合同变化不同步调用方、测试、文档
7. 禁止架构不分骨干与外围——复杂性压外围，骨干保持简洁稳定
8. 禁止跳过设计模式评估——须判断能否用设计模式优化架构
9. 禁止架构变更不产出 ADR——任何影响模块边界、数据流、技术选型、公共接口的变更必须记录架构决策
10. 禁止缺少同类实现或本仓先例即自行设计架构——先查本仓、项目文档、历史 ADR、依赖源码和既有计划；只有本地证据不足、用户要求或外部事实会影响决策时才联网搜索同类实现
11. 禁止把运行时校验作为默认架构策略——优先用类型、编译期约束、数据所有权、边界合同和测试保证正确性；确需新增运行时校验时，必须说明触发频率、热路径影响、性能成本、替代方案，并请求用户确认后才能进入实现
12. 禁止把拷贝作为默认隔离手段——优先明确数据所有权、不可变边界、只读视图、局部更新和生命周期；确需新增拷贝逻辑时，必须说明拷贝对象、数据规模、触发频率、热路径影响、替代方案和必要性
13. 禁止薄而无意义的 adapter——不要为“以后可能换实现”创建只做透传、改名、同形映射或一行转发的中间层；adapter 必须承担真实协议转换、生命周期隔离、错误语义转换、第三方 API 稳定化或跨边界适配
14. 禁止不合理的冗余数据流动——不要让全量数据在模块、hook、store、pipeline、事件之间反复搬运、复制、归一化或重新计算；必须从架构上明确单一数据源、数据所有权、最小载荷、增量更新、消费点就近派生和失效边界，不能靠新增运行时校验、拦截器或字段白名单硬性防止
15. 禁止为了转换而转换的形式主义——不要在 DTO、VO、Entity、ViewModel、Normalized、Payload、State、Event 等命名之间做同形转换、改名转换或层层包装来制造“架构感”；只有跨协议、跨持久化模型、跨信任边界、语义确实改变或消费形态明显不同，转换层才成立
16. 禁止下游用近似字段组合冒充缺失语义字段——功能需要某个语义字段而数据流没传时，应从架构上补齐上游字段衔接、类型合同、事件/API payload 和持久化/派生位置；不得因为上游没传，就在下游用其他字段拼凑、推断、猜测或近似实现该字段的功能
17. 禁止 DataOps AI 语义事实源分叉——涉及 AI runtime、read-model、工具结果、任务、统计或回放时，Pi 心智模型下 `NormalizedAgentEvent` 是唯一语义事实源；不得从 raw payload、metadata、activity title/status、session.jsonl、相邻消息、消息顺序或旧字段回推语义
18. 禁止前端跨多组件状态靠层层传递——Vue 跨多个组件、兄弟组件、深层子树或跨页面共享的数据流，应优先用 Pinia 管理领域/应用共享状态，用 provide/inject 管理局部子树上下文和依赖；React 跨多个组件、兄弟组件、深层子树或跨页面共享的数据流，应优先用 Zustand store 管理；props/emit/ref、props/callback/useState/useReducer 只用于直接父子通信或组件内部局部状态
19. 禁止把重构设计成长期兼容迁移——重构必须一步到位收敛到新合同、新数据流和新模块边界；不得规划旧路径并行、新旧字段双写、兼容桥、fallback 分支或“先保留以后删”的临时层
20. 禁止按功能点、文件或小编辑安排测试——同一大阶段全部代码、类型、调用方、迁移、fixture、测试代码和文档完成并通过代码评审后，才进入 verification 集中运行测试矩阵；中途最小诊断只用于解除阻塞，不算验收
21. 禁止把难以排除的问题设计成靠猜测定位——对跨模块、异步、并发、性能、状态流或复现成本高的风险点，方案中应规划可长期保留的诊断日志/trace 点；日志应使用项目既有 logger、级别和稳定标签，记录关键 ID、状态转移、耗时或分支原因，避免敏感信息、全量大 payload 和热路径无门控刷屏
22. 禁止把 fallback 作为默认架构策略——兜底、降级、回退、备用路径会增加心智模型、状态空间和数据流分叉；只有用户明确提出要加 fallback 时才允许规划，且必须说明触发条件、数据来源、状态收敛、删除成本和对主路径复杂度的影响
23. 禁止把浏览器/e2e 验证设计成每次临时逐步操作，也禁止见到重复就抽 helper——涉及登录、导航、建数据、等待、截图、控制台采集、通用断言等重复步骤时，先按 `test-governance` 确认至少两个独立稳定合同、技术职责边界、资源生命周期和直接消费者，再复用或扩展项目测试 SDK、e2e 脚本、fixture、test helper、page object；业务步骤和业务断言留在测试，一次性手工浏览器步骤只能用于探索、视觉取证或定位假设
24. 禁止忽略多线程并发修改风险——方案涉及其他线程可能同时修改的文件时，先规划文件归属、编辑顺序和当前工作目录文件夹根目录 `mailbox.md` 协调方式；不得把“覆盖、撤回或顺手改掉其他线程改动”设计成解决冲突的手段；mailbox 只保留未决消息，事项处理后立即删除对应内容，不写完成标记
25. 禁止只证明当前方案能做而不比较更简单方案——同一需求必须先问心智模型和数据流是否足够简单；优先选择模块更少、状态更少、数据路径更短、字段语义更直接、调用链更浅、测试边界更清楚的实现。若采用更复杂方案，必须说明简单方案为何不能满足需求
26. 禁止把对象冗余字段当作“方便调用”——同一语义只能有一个权威字段；不要在对象里同时保留 `name/title`、`status/state`、`id/key`、`mode/type` 这类实际含义相同的字段。需要改名时一次性改字段合同和全链路调用方，不做双字段并存
27. 禁止把思维链、隐藏推理或思考过程写入交付产物——HTML、Markdown、PDF/报告、页面文案、注释、fixture、snapshot、debug 面板、脚本内嵌数据和日志只能包含结论、决策、假设、证据和必要理由；不得包含 chain-of-thought、scratchpad、内部推理、提示词片段、系统/开发者指令或模型分析过程。必须从产物内容设计上避免泄露，不得用新增运行时扫描、过滤或校验来硬性防止
28. 禁止前端项目跳过设计系统——涉及前端新建、重构或视觉改动时，必须先用 shadcn + Tailwind CSS 定义或更新设计系统；语义 token（颜色、字体、字号、间距、圆角、阴影、动效、状态、z-index）和自定义组件/variants 是视觉事实源，页面和业务组件不得散落一次性 arbitrary class、inline style、局部 CSS 覆盖或硬编码视觉值
29. 禁止视觉效果修改绕过设计系统——任何视觉效果上的修改必须反馈并覆盖到设计系统的语义 token、主题配置、shadcn 组件 variants 或自定义组件，再由页面/业务组件消费；不得只在单个页面、单个组件或临时样式里修外观，除非明确标记为探索且不能作为最终交付方案
30. 禁止测试方案不盘点现状——涉及测试时，先查标准 runner、config、已有同合同测试、fixture/SDK、真实与模拟边界、孤儿测试和重复测试；不得直接按本次改动新建脚本
31. 禁止按实现文件机械拆测试——测试矩阵按稳定业务合同和风险组织，选择最低充分层级；不得为每个函数、字段、mapper、store action 或 CSS 声明规划独立测试
32. 禁止把源码字符串检查设计成运行时验证——标识符、函数顺序、模板片段和局部 CSS 数值不能证明功能；模块边界、依赖方向和禁用 API 才可用 AST/lint/static test
33. 禁止设计孤儿测试和伪 E2E——每个永久测试必须进入标准聚合命令；浏览器拦截目标后端链路时标为 integration，真实 E2E 不替代目标链内部模块
34. 禁止用完整内部 mock 链制造可测试性——mock 只放外部系统、时钟、随机数和明确副作用边界；跨 service/store/component 合同优先真实组合，API 合同至少一条真实 HTTP
35. 禁止把永久测试架构设计成可执行断言脚本——必须选择项目已锁定的现代 runner；无第三方依赖且不能安装时使用语言标准 runner。测试按稳定合同注册独立 case/suite，setup/teardown、timeout、mock、隔离和 reporter 用 runner 原生能力；不得规划顶层 assert、`main().catch()`、逐文件子进程或 `[PASS]` 日志。框架迁移前先治理价值、粒度与边界，不能只做语法替换
36. 禁止设计异步注册或顺序依赖的测试 case——suite/test 在收集阶段同步注册，公共环境进入 runner hook/fixture；case 不得依赖兄弟 case 的执行、数据、共享变量修改或顺序。按名称只运行任一 case 时必须仍可成立；不可拆的连续原子事务按一个稳定合同 case 设计，不为 case 数量形式拆分

## 同类实现调研

架构设计任何模块前，先查本仓源码、项目文档、历史 ADR、当前工作目录文件夹根目录的 `mailbox.md` 协调记录、依赖源码和既有计划；只有本地证据不足、用户明确要求或外部事实会改变方案时，才联网搜索同类产品/同类模块的技术实现：

1. **搜索范围**：优先本仓源码、项目文档、历史 ADR、依赖源码；必要时再查开源源码（GitHub）、技术架构文档、RFC/ADR、开发者博客、会议演讲
2. **搜索关键词**：需要联网时使用模块关键词 + 产品/项目名（如 "agent runtime stream" + codex/hermes/pi agents/claude code）
3. **实现报告**：每个本地先例或外部案例记录——来源、架构方案、模块划分、数据流、设计模式用法、优缺点、可借鉴点与需规避点
4. **决策依据**：架构决策必须引用本地先例或必要的外部案例；未联网时说明本地证据足够，禁止凭空发明

## 审查维度

每个架构方案必须逐维度过审：

| 维度 | 审查内容 |
|------|---------|
| **SOLID 原则** | 单一职责、开闭、里式替换、接口隔离、依赖倒置 |
| **安全漏洞** | 注入、认证、授权、文件操作、SSRF、加密、敏感信息泄露 |
| **产物泄露** | HTML/Markdown/PDF/报告/注释/fixture/snapshot/debug 面板/日志是否只包含可公开结论和必要理由；是否禁止写入思维链、隐藏推理、提示词片段或系统/开发者指令 |
| **代码质量** | 错误处理、性能热点、边界条件、可测试性 |
| **可观测性** | 难定位链路是否规划了可保留的诊断日志/trace 点；日志是否有稳定标签、级别门控和关键上下文，且不泄露敏感信息或输出全量大 payload |
| **测试 SDK 策略** | 是否先查 runner 原生能力和既有 support；每项共享能力是否有至少两个稳定消费者、明确 owner、技术职责、setup/cleanup 生命周期和退役条件；业务步骤与断言是否留在测试 |
| **测试治理** | 是否列出稳定合同、风险、测试层级、真实/模拟边界、已有测试处置、标准 runner 与删除项；是否避免源码字符串、白盒、mock 自证、孤儿测试和伪 E2E |
| **Runner 基线** | 是否使用 package 已声明且 lockfile 锁定的现代 runner 或语言标准 runner；是否同步注册独立 case，并使用原生 hook、timeout、mock、隔离、过滤与结构化 reporter；名称过滤时 case 是否不依赖兄弟执行；是否删除顶层断言/main 脚本和自建逐文件调度 |
| **并发协作** | 是否识别多线程同时改同一文件的风险；是否规划 `mailbox.md` 协商、文件归属和无冲突任务切换；是否禁止撤回或改写其他线程改动；已处理消息是否立即删除 |
| **运行时并发与锁** | 是否有真实并发来源与共享资源；能否先用所有权、分区、顺序流或已有事务消除竞争；锁/队列/worker 是否是最小且有明确生命周期的必要机制 |
| **简化优先** | 同一需求是否存在更简单实现；当前方案的心智模型、状态数量、数据路径、调用链、字段语义和测试边界是否足够简单 |
| **数据流治理** | 是否存在冗余流动、全量处理、重复归一化、跨层搬运；是否可改为单一数据源、最小载荷、增量处理、就近派生 |
| **前端设计系统** | 前端项目是否先定义 shadcn + Tailwind CSS 设计系统；语义 token、自定义组件和 variants 是否作为视觉事实源；视觉效果修改是否已反馈覆盖到设计系统，而不是落在局部临时样式 |
| **前端状态流** | Vue 跨多组件状态是否使用 Pinia 或 provide/inject；React 跨多组件状态是否使用 Zustand；是否存在 props/emit/ref drilling、props drilling 或 callback drilling |
| **字段衔接** | 功能所需语义字段是否从源头传到消费点；是否存在用其他字段组合近似替代缺失字段 |
| **对象字段唯一性** | 同一对象/payload/state/event/DTO 中是否存在意义完全相同的冗余字段；是否已选定唯一权威字段并同步全链路，而不是增加运行时校验 |
| **DataOps AI 事实源** | AI runtime/read-model/工具结果/任务/统计/回放是否只从 `NormalizedAgentEvent` 读取语义事实；是否存在 raw payload、metadata、session.jsonl、相邻消息或旧字段 fallback |
| **转换必要性** | 是否只是同形转换、改名转换、层层包装；若保留，必须说明语义差异、边界差异或消费差异 |
| **重构收敛** | 是否一次性切到新合同；是否残留旧路径、兼容层、fallback、双写、旧测试 |
| **Fallback 控制** | 是否存在用户未明确要求的兜底、降级、回退或备用路径；若用户要求 fallback，是否清楚说明触发条件、状态收敛和数据流分叉成本 |
| **运行时校验** | 是否存在真实可达来源、唯一 owner 是否明确、为何不能由已有边界合同承担、是否位于热路径、用户是否已确认 |
| **哈希与指纹** | 是否有真实安全、协议、内容寻址或幂等合同；是否避免把哈希/校验和/指纹作为内部理论风险的默认防御 |
| **链路边界** | 是否追踪 source 到 consumer 的完整链路；是否区分真实边界与上游保证不可达状态；是否存在重复 parse/normalize/validator/interceptor/fallback |
| **拷贝策略** | 是否新增对象/数组/大 payload 拷贝、为何不能通过所有权或只读合同避免、是否位于热路径 |
| **Adapter 必要性** | 是否只是透传/改名/同形映射；若保留，必须说明被适配双方的真实差异与删除成本 |
| **可删除代码** | 无用代码、冗余逻辑、死代码识别 |
| **设计模式** | 二十九种设计模式能否使架构更优（见下） |
| **复杂度回溯** | 局部复杂度是否暴露概念、原语、底层动作或模块边界设计不当；是否已比较更直接的领域动作与更少状态方案 |

## 设计模式评估

只对当前具体复杂度可能有效的设计模式做针对性判断；禁止为了完成清单逐一套用全部模式：

**创建型**：Factory、Abstract Factory、Builder、Prototype、Singleton
**结构型**：Adapter、Bridge、Composite、Decorator、Facade、Flyweight、Proxy
**行为型**：Chain of Responsibility、Command、Iterator、Mediator、Memento、Observer、State、Strategy、Template Method、Visitor
**扩展型**：Plugin、Hook、Dependency Injection、Event-Driven

评估目标：

- 心智模型更简单——开发者读代码能快速理解"数据从哪来、到哪去、谁改了它"
- 数据流更简单——减少跨模块的隐式依赖与双向数据流
- 数据流更瘦——跨边界只传必要字段、标识符或增量，避免为了下游便利提前传播全量对象
- 每个模块复杂度可控——单个模块的分支/状态/依赖数保持在可单元测试覆盖的程度
- 单元测试只证明局部合同；跨模块、序列化、数据库、浏览器与用户路径必须由对应 contract/integration/e2e 层证明

不适用则不评估、不强行套用；适用则注明用了哪种、解决了什么具体复杂度、对数据流的影响。评估 Adapter 时必须额外说明被适配双方的接口、语义或生命周期差异；若只是函数重命名、参数转发或同形对象转换，应直接合并到调用方或被调用方。无论是否使用设计模式，都必须比较至少一个更简单实现路径，并说明为什么最终方案让心智模型和数据流更清楚。

## 解耦原则

- **尽量用 hooks 和 plugin 模式解耦**——模块通过 hook 注入行为、通过 plugin 扩展能力，而非继承或硬编码依赖
- **模块要粗**——功能内聚的代码放一起，不过度拆分；避免一个功能散布在五个文件里
- **hook 要少**——每个模块暴露的 hook 点不超过必要数量，hook 越多心智负担越重
- **plugin 走接口**——plugin 通过声明的能力接口参与 pipeline，禁止 plugin 直接访问宿主内部状态；不要用字段白名单、写保护、exact object 合同或 unknown-field rejection 模拟“防乱写”
- **plugin 字段要宽容**——插件合同只要求插件提供宿主运行所需的必要字段；允许插件携带额外字段，宿主不得因未知额外字段拒绝插件、报错或强行剥离扩展数据，除非额外字段越权访问宿主内部状态或破坏明确安全边界
- **数据流要瘦**——源数据只在拥有者处维护，跨边界传必要字段/ID/增量；派生数据在消费点就近计算或缓存，禁止在多层之间传递同一份全量快照
- **DataOps AI 事实源要唯一**——涉及 AI runtime/read-model/工具结果/任务/统计/回放时，`NormalizedAgentEvent` 承载语义事实；Pi/session/jsonl/raw payload 只能作为运行时或调试证据，不能成为语义 fallback
- **Vue 状态流要集中或就近注入**——跨页面/跨模块共享状态放 Pinia；页面或功能子树内的上下文、服务、控制器、只读状态用 provide/inject；不要让中间组件只为转发 ref、props 或 emit 而参与数据流
- **React 状态流要进 Zustand**——跨页面/跨模块/跨多个组件共享的领域或应用状态放 Zustand store；`useState`/`useReducer` 只留给组件内部或明确拥有者的局部状态；props/callback 只用于直接父子输入和局部事件，不让中间组件只为转发 props、callback 或 state 而参与数据流
- **字段要正交且唯一**——一个语义字段缺失就补该字段的来源和传递链路；同一对象内同一语义只保留一个权威字段；不要让下游用多个弱相关字段组合出“看起来像”的结果，也不要用两个同义字段表示同一事实
- **转换要有语义**——转换必须改变协议、语义、持久化形态、信任边界或消费形态；仅为匹配分层命名而转一遍对象是噪音，应删除
- **重构要收敛**——架构方案只能保留目标形态；旧入口、旧字段、旧状态、旧测试和兼容 fallback 必须纳入删除清单，同步清掉
- **fallback 要用户先提出**——不要主动用 fallback 消解设计矛盾、异常路径或数据缺口；用户未明确要求 fallback 时，方案只能修正主路径合同、字段衔接、状态边界和错误暴露
- **拷贝要谨慎**——不要为“安全感”全量 clone、深拷贝或重复映射大对象；需要隔离可变性时，先收紧写入边界和所有权，再考虑最小范围拷贝
- **adapter 要有重量**——adapter 只能用于真实边界差异；薄透传层会增加文件跳转、命名负担和测试噪音，应优先删除
- **reducer 要纯**——所有状态变更通过纯函数 reducer 表达，禁止 reducer 内发请求、读写 DOM、触发副作用
- **简单方案优先**——同一需求先尝试直接补合同、收紧所有权、减少状态、缩短数据路径和就近派生；不要先引入新层、新 store、新 pipeline、新事件或新转换。更复杂方案只有在能减少整体复杂度时才成立
- **产物只放可公开内容**——任何生成的 HTML、文档、报告、测试产物或可持久化调试信息都只承载用户需要看到的结论、决策、假设、证据和简短理由；内部思考、chain-of-thought、scratchpad、提示词和系统/开发者指令不进入产物数据流
- **前端设计系统先行**——前端项目先定义 shadcn + Tailwind CSS 设计系统，再设计页面；语义 token、主题变量、组件 variants 和自定义组件承载视觉规则，业务页面只组合和消费设计系统
- **视觉改动回写设计系统**——按钮、表单、卡片、布局、颜色、间距、阴影、圆角、动效、状态样式等视觉效果变化，要先更新设计系统 token 或组件定义，再同步到使用点；不要让局部覆盖成为新的事实源

## 产出

- **同类实现报告**：参考的本地先例或必要外部案例、架构方案、模块划分、数据流、可借鉴点与需规避点；未联网时说明本地证据足够
- **前端设计系统方案**：涉及前端时，先给出 shadcn + Tailwind CSS 设计系统定义，包括语义 token、主题变量、自定义组件、variants、复用边界和视觉改动回写规则；后续视觉效果修改必须反馈覆盖到设计系统，再由页面/业务组件消费
- **技术方案**：模块边界、数据流、选用的设计模式及理由、hook/plugin/reducer 设计、审查维度逐项结论；必须说明数据所有权、跨边界载荷、增量/全量处理选择、派生数据位置和失效条件；必须列出同一需求考虑过的更简单实现、未采用原因，以及最终方案如何保持心智模型和数据流简单；涉及交付产物时，说明 HTML、Markdown、报告、注释、fixture、snapshot、debug 面板、日志等只输出结论、决策、假设、证据和必要理由，不写入思维链、隐藏推理、scratchpad、提示词片段或系统/开发者指令；涉及难定位链路时，列出计划保留的诊断日志/trace 点、日志标签、触发条件、关键上下文和敏感信息规避方式；涉及 DataOps AI 语义消费时，必须说明 `NormalizedAgentEvent` 字段来源、传递链路和消费点，并列出 raw payload、metadata、session.jsonl、相邻消息、旧字段 fallback 的删除清单；涉及测试时，附测试矩阵：稳定合同、风险、最低充分层级、真实/模拟边界、已有测试保留/合并/改造/删除、标准 runner、批量命令与触发时机，以及复用当前开发数据库的数据创建/迁移、修改和清理责任；不得规划为每次测试创建临时测试库、源码字符串运行时证明、内部完整 mock 链、未注册脚本或错误命名 E2E；涉及测试复用时，每项 SDK/helper/fixture/page object 必须列 owner、至少两个现有稳定消费者、抽取依据、输入输出、承担和不承担的职责、setup/cleanup 生命周期、直接导入路径与退役条件，业务步骤和断言留在测试；涉及并发修改风险时，列出文件归属、冲突时 `mailbox.md` 协商方式、可先做的无冲突任务和恢复修改条件；重构方案必须列出旧路径/旧字段/旧测试/兼容层删除清单，并确认不保留 fallback；如用户明确要求 fallback，附用户要求记录、触发条件、状态收敛方式、数据流分叉成本和删除成本；Vue 前端跨多组件状态须说明选择 Pinia、provide/inject 或局部 props/emit 的理由；React 前端跨多组件状态须说明选择 Zustand 或局部 props/useState/useReducer 的理由；功能所需语义字段必须列出来源、传递链路和消费点；对象字段合同必须确认同一对象内没有意义完全相同的冗余字段，若发生字段改名或收敛，列出唯一权威字段和旧同义字段删除清单；如涉及转换层，附源模型、目标模型、真实差异、保留理由与删除成本；如涉及 adapter，附被适配双方差异、保留理由与删除成本；plugin 合同须注明必要字段与额外字段处理策略；如涉及拷贝逻辑，附必要性、数据规模、触发频率、性能影响与替代方案；如涉及运行时校验，附必要性、性能影响、替代方案与用户确认记录
- **体验映射**：对每项关键 UI、交互和功能变化列出用户阻碍、改善后的主路径、失败恢复和可观察结果；说明为何该方案比更少状态、更少步骤或更少功能的替代方案更能改善用户体验
- **ADR**：每条架构决策记录——决策内容、背景与动机、可选方案及取舍、后果与风险
- **任务清单**：拆解与依赖序，每条任务有完成条件
- **阶段测试门禁**：列出大阶段边界、阶段内全部功能点、统一完成条件、进入 verification 的前置条件，以及只在阶段末集中执行的测试矩阵；不得给每个功能点附测试命令
- **系统测试矩阵**：正常功能只列项目既有 Playwright 的 UI 用户路径、真实前后端链路、开发数据库数据生命周期和可见断言；不得列其他测试层级或 mock/直调路径
- **边界合同**：涉及边界时，附完整 source-to-consumer 链路、非法值可达性证明、唯一校验/解析/拦截 owner、输入/输出合同和下游不重复处理假设；不得为上游已排除的理论状态安排代码或测试
