# 月报转写

**输入**零散素材（+ 可选模板），**输出**一份合规的中文项目进度月报 DOCX。

你的任务是**转写**，不是创作：把杂乱内容整理成合文风、合表达意图、合排版的文档。素材里没的事实不要编；缺的信息去问，不要猜。

```text
素材(可选模板) → ①问清缺项 → ②抽事实 → ③按文风改写 → ④排版 → ⑤验收
```

---

## 0. 开工先问

**模板是可选输入。** 有模板就对齐它；没有就用第 4 节的内置版式从零起草 —— 两种情况都不影响交付。

材料不全时，先一次性问清下面这些，**不要靠猜**：

| 要问什么 | 用途 | 缺了会怎样 |
|---|---|---|
| 项目名 + 报告周期 | 标题、`X年X月完成情况` | 标题写错，整份废 |
| 本月素材在哪 | 决定去哪抽事实 | 只能编 |
| 有没有上月模板 / 上月报告 | 有→对齐版式与计划段写法；无→内置版式 | 版式自说自话 |
| 本期进度百分比 + 下期目标 | 写进「本月重点任务」 | **禁止自行推算**，必须业主给 |
| 大项有哪几个、要不要增删 | 报告骨架 | 结构不对，全篇返工 |
| 有没有必须出现 / 必须删掉的内容 | 口径 | 业主打回 |
| 字数上限 | 控制详略 | 越写越长 |

**只问真正缺的。** 素材里已经明确的不重复问，一次问完不要来回。

## 1. 抽事实

从素材里逐条抽出「本月实际做了什么」，每条都要有出处。

**有 git 仓库时**，逐条去仓库核验，不要凭印象概括：

```bash
git log --since='2026-09-01T00:00:00+08:00' --until='2026-10-01T00:00:00+08:00' \
  --pretty='%ad %h %s' --date=short
```

**报提交量必须写全时区边界。** 纯日期 `--since=2026-09-01` 按本地时区解析且比较 committer date，会静默丢掉当月 1 日北京时间的提交 —— 实测两个仓库分别漏掉 **2 条 / 56 条**。写成「dataops 137 / dsh-plus 1674（北京日历月，main 主干）」，否则别人复算对不上。

**判定证据强度**：

| 判定 | 含义 | 处理 |
|---|---|---|
| SUPPORTED | 找到具体提交 / 工单 | 保留 |
| WEAK | 只有间接证据 | 收敛措辞，去掉「持续完善」等无法证实的加强词 |
| UNSUPPORTED | 全库零命中 | **删掉，或先向业主取口径** |

**UNSUPPORTED 不等于没做过** —— 等保材料、报送、评审这类工作天然在仓库之外（纸质、邮件、微信）。但仓库支撑不了的主张，必须从别处取口径。**严禁**写无法证实的具体结论（例如「等保测评定为三级」）。

## 2. 文风

定稿的语感基准。转写时按这套句式改写，不要保留素材里的口语、工单黑话、技术术语堆砌。

**句式模板**（从定稿反推）：

| 位置 | 句式 |
|---|---|
| 大项总述 | `本月重点任务：围绕A、B、C开展建设；完成D，启动E；整体开发进度X%。` |
| 完成项 | `完成X，完善Y。` / `开展X。` / `推进X。` / `修复X问题。` / `对接X。` / `处理X。` |
| 每条开头 | 动词打头：完成 / 开展 / 推进 / 完善 / 支持 / 修复 / 处理 / 对接 |

**硬性文风约束**：

- **一条一个动作**，单条 20–45 字，不堆砌。
- **少写技术细节。** 业主看的是业务结果，不是实现方案（`改用批量写入` → `提升运行稳定性`）。
- **百分比进「本月重点任务」**，不单列「研发进度（X%）」段落。
- **正文不得出现内部研发产品名**，一律换成对外名称。扫描要覆盖**全部 XML 部件**，不能只扫 `document.xml`：

```bash
cd /tmp && rm -rf scan && mkdir scan && cd scan \
  && unzip -q "/path/交付件.docx" \
  && grep -rl "Deepseek\|Harness" . || echo "干净（无输出=通过）"
```

- 全角标点、句末句号；不用「我们」、不写人天投入。
- **口语化指令要落到字面。** 业主说「改成铺开使用 AI 能力啊」，就落到具体段落改字，并回报改后原句。

## 3. 结构

```text
<项目名>202609进度报告                      ← 标题
<项目名>2026年9月完成情况：                  ← 副标题
一、<大项A>：                               ← 一级标题
  本月重点任务：……                          ← 总述（含进度百分比）
  （一）<子项>                              ← 二级标题（小项 > 8 时才用）
    （1）……
二、<大项B>：
  …
<项目名>2026年10月计划：                     ← 计划段
1、……
2、……
```

- **单个大项下的小项 ≤ 8 个。** 超过就拆二级标题分组；**不等于可以砍内容**。
- **「本月重点任务」每个大项只出现一次**，是该大项总述。
- **计划段用 `1、2、3、` 编号句一气写完**，不按项目分小标题；若给了模板，以模板的计划段写法为准。
- **「下月计划」必须相对上月计划有实质更新。** 逐条自问：这条比上月新增了什么？只换措辞不算。
  - 好：上月「推进上架原子能力」→ 本月保留并追加新交付目标。
  - 坏：上月「继续开发完善平台」原样搬运。
  - 上月计划里丢掉的内容要**捡回来**。
- **小项条数守恒**：上月 N 条 → 本月保留 N 条或明确增减，不静默从 5 条缩到 3 条；缩减必须**主动说明并请业主确认**。

## 4. 版式

### 有模板

先从模板**实测**取值，不要凭印象 —— 相邻月份常只差 1–2pt：

```bash
python3 - <<'PY'
import re, zipfile
doc = zipfile.ZipFile("模板.docx").read("word/document.xml").decode("utf-8")
for p in re.findall(r"<w:p\b.*?</w:p>", doc, re.S):
    t = "".join(re.findall(r"<w:t[^>]*>(.*?)</w:t>", p, re.S))
    if not t.strip():
        continue
    ppr = re.search(r"<w:pPr>.*?</w:pPr>", p, re.S)
    ppr = ppr.group(0) if ppr else ""
    sz = re.findall(r'<w:sz w:val="(\d+)"', p)
    sp = re.search(r"<w:spacing[^>]*/>", ppr)
    ind = re.search(r"<w:ind[^>]*/>", ppr)
    jc = re.search(r'<w:jc w:val="(\w+)"', p)
    bold = bool(re.search(r'<w:b\s*/>|<w:b w:val="(?:1|true)"', p))
    print(f"sz={sz} bold={bold} jc={jc.group(1) if jc else '-':7s} "
          f"{sp.group(0) if sp else '-':60s} {ind.group(0) if ind else '-'}")
    print("   ", t[:40])
PY
```

### 无模板（内置版式）

`w:sz` 为半磅：24 = 12pt，28 = 14pt，36 = 18pt。

| 角色 | 字号 | 加粗 | 对齐 | 段前/段后 | 缩进 |
|---|---|---|---|---|---|
| 文档标题 | 18pt (36) | 是 | 居中 | 240 / 360 | left 0 |
| 副标题（…月完成情况：） | 12pt (24) | 是 | 左 | 60 / 60 | left 0 |
| 一级标题（一、二、三、） | 14pt (28) | 是 | 左 | 240 / 120 | left 0 |
| 二级标题（（一）（二）…） | 12pt (24) | 是 | 左 | 120 / 60 | left 0 |
| 列表项（（1）（2）…） | 12pt (24) | 否 | 左 | 60 / 60 | **left 480** |
| 计划段编号（1、2、…） | 12pt (24) | 否 | 左 | 60 / 60 | **left 480** |
| 总述段 | 12pt (24) | 否 | 左 | 60 / 60 | **left 480 + firstLine 480** |

页面：A4，`pgSz 11906×16838`，`pgMar` 上下左右均 1440 twip（2.54cm）。字体 `仿宋`，`ascii`/`hAnsi`/`eastAsia`/`cs` **四处都要设**，缺一处就回退。

**陷阱**：加粗写在 **run 的 `rPr`** 里，不在 `pPr`。只查 `pPr` 会误判「标题没加粗」，然后重复加粗。

**分页**：计划段较短、标题会落页底成孤行时，在计划标题段加 `<w:pageBreakBefore/>`。实测上月模板该属性为 `False`，所以这是**对模板的刻意偏离**，加了要写进交付说明。

## 5. 操作流程（OfficeCLI）

```bash
# 0. 定位二进制（常在 ~/.local/bin）
export PATH="$PATH:$HOME/.local/bin"

# 1. 先读，不急着改
officecli view 交付件.docx outline
officecli view 交付件.docx text                       # 带 paraId 的全文
officecli get 交付件.docx '/body/p[69]' --depth 3 --json   # 单段格式详情

# 2. 批量改（同一阶段一次提交）
officecli set 交付件.docx / --find '旧措辞' --replace '新措辞'

# 3. 落盘 + 验收
officecli validate 交付件.docx --json
officecli view 交付件.docx issues --json
```

- `set` 用 `--find/--replace` 是**顶层参数**，不要再加 `--prop`。
- 改动有落盘延迟 —— 改完立刻 `ls -la` 确认 mtime 已更新。
- **就地改原 DOCX，不要另存副本**；不要把 HTML / PNG / Univer 预览当交付物。
- 交付件路径要能在同目录渲染出最终 DOCX，供聊天文件链接与 Better Sidebar 打开。

## 6. 验收

- [ ] `validate --json` 通过；`issues` 只剩模板本就存在的「首行缩进」提示类告警
  - 对照基线：把模板与内容稿也跑一遍 `issues`，数字相当才叫「本来就存在」
- [ ] 全部 XML 部件扫描，内部产品名 0 处
- [ ] 计划段旧措辞 0 处残留
- [ ] 计划段相对上月有实质更新；条数变化已向业主说明
- [ ] 单大项小项数 ≤ 8
- [ ] 「本月完成情况」字数在上限内
- [ ] 计划段分页已确认（加了 `pageBreakBefore` 则写明）
- [ ] 待确认项已列出，未擅自修改
- [ ] 交付件为最终 DOCX 绝对路径

**字数用 `len()` 数全角字符，不要用 `officecli stats` 的 `words`**（中文严重低估），**也不要解析 `officecli view text`** —— 后者每行带 `[/body/p[@paraId=XXXX]]` 前缀，前缀含内层 `]`，常规正则剥不干净，实测把 **1891 字报成 3619 字**。直接读 `document.xml`：

```bash
python3 - <<'PY'
import re, zipfile
doc = zipfile.ZipFile("交付件.docx").read("word/document.xml").decode("utf-8")
ps = re.findall(r"<w:p\b.*?</w:p>|<w:p\b[^>]*/>", doc, re.S)
texts = ["".join(re.findall(r"<w:t[^>]*>(.*?)</w:t>", p, re.S)) for p in ps]
i_done = next(i for i, t in enumerate(texts) if t.endswith("9月完成情况："))
i_plan = next(i for i, t in enumerate(texts) if t.endswith("10月计划："))
print("完成情况字数:", len("".join(texts[i_done + 1:i_plan])))
PY
```

数「小项个数」同理按段数数（`（1）（2）…` 各占一段），不要用 `words`。

## 7. 反面清单

- ❌ 计划段照抄上月 → 最高频打回原因。
- ❌ 缺信息靠猜（项目名、进度百分比、大项构成）→ 先问。
- ❌ 拿旧预览 PNG/HTML 判断交付状态 → 预览比 DOCX 旧几小时很常见。**一律以 DOCX 为准。**
- ❌ 只扫 `document.xml` 就宣布「无内部产品名」→ 页眉页脚/属性部件常有残留。
- ❌ 只查 `pPr` 判断标题加粗 → 加粗在 run 的 `rPr` 里。
- ❌ 用纯日期 `--since=2026-09-01` 报提交量 → 边界提交被静默丢弃，数字无法复算。
- ❌ 报告里写无法证实的具体结论（如「等保测评为三级」）→ 先取材料或问业主。
- ❌ 小项从 5 条静默缩到 3 条 → 变化必须显式说明并请确认。
- ❌ 擅自「顺手修正」业主没提的地方 → 列出待确认项，让对方定。
- ❌ 写字数用 `stats` 的 `words` 或解析 `view text` 输出 → 数字不可信。
- ❌ 把模板当必需输入 → 没模板就用内置版式起草。
- ❌ 交付时另存副本或改成 HTML/PNG → 就地改原 DOCX，交付绝对路径。
