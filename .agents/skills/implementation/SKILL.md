# implementation

## 最高优先级禁令

以下规则优先于本技能的其他规则，后续条款不得作为例外：

1. **禁止过度锁与并发设计**：没有真实并发入口、共享资源及用户/协议合同，不设计锁、队列、worker、并发池或异步编排。
2. **禁止 smoke/冒烟测试**：服务存活、健康检查、页面可打开或元素存在只能用于环境就绪，不能作为测试或验收证据。
3. **禁止内部防御式编程**：不为理论非法状态增加 optional 分支、默认值、吞错、重复校验、过滤、fallback 或兼容路径；真实 ingress 仅由唯一 owner 处理。
4. **谨慎看待竞态，大部分情况下不可能出现竞态**
5. **不预设边界情况**：没有用户反馈、真实使用证据或既有明确合同，不把想象中的边界情况写成设计、代码、测试或结论；先完成主路径，后续按实际反馈处理。

## 完整用户路径优先

- 实现目标是可交付的完整用户结果，不是最小 diff。只要闭环需要修改公共合同、调用方、原型、生成物、状态、错误提示或测试，就必须一起完成。
- 禁止把必要的后端能力、菜单动作、空态、加载态或失败恢复留作“后续”；优先让用户路径简单、可发现、可回到成功状态。
- 扩大改动前先确认它直接服务于当前用户目标或架构一致性；无关重构仍不纳入本阶段。

## 体验目标落地

- 每项实现必须落实已定义的用户体验改善：让界面信息更清楚、操作更直接、功能更能完成目标，或让失败更容易理解和恢复。不能对应用户阻碍和可观察改善的改动不实现。
- 不以增加控件、动画、步骤、状态或功能数量替代体验优化；优先删除摩擦、减少等待与记忆负担、提供明确反馈，并保持主路径可预测。
- 实现中发现 PRD 或方案无法让用户顺畅完成目标时，暂停局部堆砌，回到产品/架构阶段修正用户路径。

## 局部复杂度实现门禁

- 遇到嵌套分支、状态组合、调用顺序依赖、难以命名的 helper、反复转换或参数旗标膨胀时，先暂停局部堆砌；检查是否应收敛业务概念、状态 owner、原语或底层动作，而不是只把代码拆得更碎。
- 若根因跨模块、涉及数据所有权、概念边界或状态机，回到 `architecture-planning` 更新方案后再实现。只在真实变化轴明确时采用设计模式；不得用 facade、factory、strategy 等名称包装仍然混乱的流程。

## 运行时并发与锁实现门禁

- 不为“以防同时发生”添加 mutex、lock、semaphore、全局队列、worker、并发池、`Promise.all` 扇出或自定义调度。先确认真实同时触发的入口和共享可变资源，并优先按方案收敛所有权、分区、单写者或顺序流程。
- 只有方案已定义真实并发合同才实现最小机制；锁定范围、获取/释放、超时/取消、错误语义和并发上限必须由指定 owner 管理。发现需要多锁、跨层锁或以锁修补状态不清时，回到 `architecture-planning` 重审。

## 系统测试实现

- 正常功能开发只新增或改造项目已有的 Playwright 系统测试。一个 case 从 UI 入口完成用户操作，并验证真实前端、后端和当前开发数据库共同产生的可见结果、状态刷新和必要恢复。
- 测试步骤和业务断言只能经 Playwright 页面操作完成；禁止 `page.route`、直接 HTTP/API/SQL、mock/stub、unit/component/contract/visual/performance 测试或白盒断言。不要为本阶段保留另一套测试路径。
- 不新增或保留 smoke/冒烟测试；仅检查启动、健康、首页可访问或单个元素存在的脚本不属于系统测试，删除或降为环境就绪动作，不能作为通过证据。

## 前置

- 技术方案 + 任务清单（来自 architecture-planning）
- 涉及新增、修改或迁移测试时，读取并遵守 `test-governance` 及技术方案中的测试矩阵

## 路径口径

- 本技能中的“根目录/当前根目录”指本轮任务开始时探测到的当前工作目录文件夹根目录（`pwd` 对应的工作区根目录），不是该工作目录下某个子项目、子仓库或模块的项目根目录；例如当前工作目录为 `/root/projects` 时，根目录就是 `/root/projects`，不是 `/root/projects/dataops`。

## mailbox 消息生命周期

- `mailbox.md` 只保存当前未解决、需要协商的消息，不是历史日志、任务清单或完成记录。
- 消息对应的冲突、文件占用或协作事项已处理、完成、释放或经用户确认后，立即删除该消息对应内容；不要追加“已处理”“已完成”“已释放”标记，也不要留下空壳。
- 删除只针对已处理消息，其他线程未处理的内容必须原样保留；一条消息混有已处理和未处理内容时，只删已处理部分，保留未决事项。
- 新增消息前先读取当前内容，避免重复创建；继续协作时只维护未决内容，已删除内容不需要恢复为历史记录。

## 功能模块并行

- implementation 需要并行时，只按 architecture-planning 已定义的独立功能模块或纵向业务切片分配；每个线程对所属模块的生产代码、合同、调用方、迁移、测试代码和文档负责到底。
- 禁止把同一功能拆成“一个线程写接口、一个线程写实现、一个线程写测试、一个线程写文档”，也禁止按前端/后端/数据库等任务类型切开后依赖频繁交接；这些工作在所属功能模块内完成。
- 并行前先冻结模块间最小输入输出合同和文件 owner。共享类型、公共 API、schema、基础设施或同一热点文件由唯一 owner 修改，其他模块消费其合同，不并发抢写。
- 模块之间存在强顺序依赖、共享状态尚未收敛或集成点不清时，先完成上游模块再启动下游模块；不得为了提高线程数量制造伪并行。

## 后端声明式开发

- 实现后端功能时，优先用当前框架原生声明式 API 表达装配和策略：注解/装饰器、模块 metadata、DI provider、schema、路由、权限、校验、事务、序列化、拦截器、事件订阅和任务调度。不要在多个 service/controller 中重复命令式注册或分支判断。
- 扩展能力必须优先注解驱动：实现公开 provider/interface 合同，标注框架可发现的注解/装饰器，并进入所属模块的 DI/discovery 范围；不得新增中央 `switch`、手工 registry、文件名扫描、源码扫描或第二套兼容装配路径。
- 新增自定义声明时，复用框架 metadata/DI/schema API，明确可声明目标、参数类型、发现范围、重复/冲突行为、实例作用域和启动失败语义。声明应是唯一事实源，缺失或冲突在装配边界明确失败，不在运行主路径追加 fallback。
- 注解和声明只承载注册、策略与跨切面元数据；业务规则、有状态流程和调用顺序留在显式 service/handler/use case。装饰器工厂、schema hook 和 metadata resolver 保持类型化、可预测且无隐藏 I/O，不得吞错或隐藏业务分支。
- NestJS 优先复用 `@Module`、`@Injectable`、`@Controller`、guards、pipes、interceptors、filters、custom metadata 与 DiscoveryService。不得只为“看起来声明式”增加不参与框架发现、仅转发调用或只改名的空装饰器/薄 DSL。

## 链路边界实现门禁

- 编码前先沿 `source -> transport/API/event -> schema/parser -> service/use case -> persistence/state -> consumer` 追踪待处理值，确认非法值的真实来源、可达路径和首次拥有边界的层；不能只根据某个函数签名或局部“理论输入”增加防御。
- 以端到端合同而非局部假设作为默认前置条件。真实链路证明不可达时，不为“可能是 `undefined`/非法”的函数入参增加 validator、fallback、吞错 `try/catch`、类型扩张、额外拷贝或重复解析；保留清晰前置条件，让真实合同破坏在其 owner 处修复。
- 外部 HTTP/event、用户输入、数据库历史数据、插件/第三方协议、跨信任域和不可信反序列化是独立真实边界。上游 schema、类型、解析器或框架装配已经排除的非法值，视为下游合同保证，不在 controller/service/store/consumer 重复拦截。
- 每个边界条件只保留一个校验/解析/归一化/拦截 owner，并把验证后的最小字段或状态传给下游。下游可以依赖该合同；只有存在绕过既有 owner 的真实入口，才在该入口补齐处理。
- 新增运行时校验、fallback、validator、interceptor 或重复 schema parse 前，必须说明非法值来源、已有 owner、已有 owner 不能承担的原因、触发频率/热路径成本及不会造成重复处理或数据流分叉的理由；未获用户确认不得实现。
- 不为内部“保险”给 payload、对象或中间结果追加 hash、checksum、fingerprint、内容比对或碰撞处理。只有技术方案已证明密码/签名/完整性、外部协议、内容寻址或幂等合同需要时，才在指定 owner 实现；不得让下游重复计算或以哈希掩盖所有权和数据流问题。
- 禁止防御式编程：内部链路不为理论非法输入追加 optional 分支、默认值、吞错 `try/catch`、重复 validator、过滤、fallback 或兼容路径。遵守已验证合同；真实入口缺少 owner 时只在该入口补齐，不在所有消费者复制防御。

## 数据链路字段完整性

- 下游功能需要的语义字段，优先从权威生产者补齐，并贯通 `source -> transport/event -> schema -> persistence/state -> consumer`；字段应随主链路一次传递，而不是由消费端猜测、拼接或回查。
- 禁止把额外查询、轮询或补拉当作数据缺口的默认补丁。先判断能否通过新增、保留或传递最小权威字段消除额外 I/O、重复状态与第二数据路径。
- 只有源头不能提供该字段、跨系统对账是明确产品合同，或数据时效要求确实不同于主链路时，才设计补拉；必须说明唯一事实源、触发频率、批量/并发边界、失败语义和为什么字段贯通不能满足。

## 响应式状态实现

- 优先让 UI 从用户操作响应、服务端事件、WebSocket/SSE/订阅或唯一 store 的受控更新中获得新状态；不要以 `setInterval`、递归 `setTimeout`、重复 fetch 或组件级多处拉取维持“实时”。
- 事件订阅必须由明确 owner 创建和释放，并处理断开、重连、重复事件、过期事件和页面卸载；状态只在唯一 owner 更新，再由真实消费 UI 响应式渲染。
- 轮询只可用于已证明无推送/回调能力的外部系统，并须实现退避、并发禁止、频率与总时限上限、取消/卸载清理和用户可见状态；不得无条件常驻运行。

## 断线恢复实现

- 上游具备持久事实源和稳定原生游标时，按其已定义的增量读取/订阅合同恢复：保存最后确认的原生游标，重新连接后从该游标向上游补读、在唯一适配边界投影，再继续接收实时事件。传输层断开只结束传输，不得终止、阻塞或改变上游任务本身。
- 不实现本地事件缓冲、journal、replay 队列、outbox、补偿 watcher 或断线后的自动命令重试；不把未持久化 token delta 或临时进度伪装为可恢复事实。上游没有可证明的无缺口恢复合同，停在边界并回 architecture-planning 定义合同，不以额外状态机或队列绕过。

## 大阶段实现门禁

- implementation 覆盖 architecture-planning 在计划文档中定义的整个大阶段。一个计划大阶段可以包含多轮实现、多个任务和多次内部调整；阶段内始终停留在 implementation，直到所有功能点、生产代码、类型、调用方、迁移、fixture、测试代码、旧路径删除和文档一起收敛到目标形态。
- 实现阶段可以编写和自查 Playwright 系统测试代码，但不进入正式 code-review，也不执行阶段验收命令。计划大阶段全部实现完成后才移交 code-review，复评通过后由 verification 集中运行系统测试矩阵。
- 不以“小批次”“安全起见”“先看是否通过”为理由反复启动 runner、浏览器、数据库或服务。测试执行不是编码进度反馈机制，阶段任务清单只记录实现状态和未决问题。
- 只有当前实现被阻塞、无法继续且需要判定一个具体根因假设时，才允许运行一次最小诊断命令或临时探针；诊断结果只用于定位，不标记功能通过、不替代集中测试，也不扩成逐点回归。
- verification 发现失败后，按共同根因回到 implementation 一次修完整批关联问题，再经过 code-review 复评；不得每修一个失败 case 就立刻重跑。

## 开发数据库测试实现

- 涉及数据库的测试代码、fixture、support 或迁移准备时，默认针对当前可任意修改的开发数据库实现；不得为单个测试、case 或测试批次新增临时测试库、数据库容器或切换数据库配置。
- 系统测试的业务操作与断言只经 Playwright UI 完成。开发数据库的数据生命周期必须可追踪、可清理，且不依赖新的数据库实例、直接 SQL 或后端测试 SDK。
- implementation 阶段只完成这些测试资产，不执行测试命令；实际的开发数据库操作留给 verification 的集中测试阶段，除非为了定位阻塞根因运行一次最小诊断。

## 移动端实现范围

- 用户未明确要求移动端适配、响应式布局或小屏交互时，只实现需求指定的目标平台和视口；默认按当前桌面目标交付，不新增移动端断点、触摸交互、移动端专属组件或小屏兼容层。
- 不为“看起来更完整”扩展移动端 CSS、布局、路由或测试；用户明确提出后，再把移动端行为作为独立合同同步到类型、组件、fixture、测试和文档。

## 原型 HTML 数据复现

- 复现原型 HTML 的 UI 时，目标 UI 必须复用原型使用的 mock 数据或其字节等价快照；保留字段值、类型、数组顺序、空值/缺失值和筛选、排序、分页、时间状态，不得用另一份近似数据掩盖差异。
- 对比前先确认原型和目标 UI 加载的是同一数据版本、视口和交互状态。发现数据不一致时先将比较标记为“不可比”，修正 fixture/data contract；不得调整 CSS 或用视觉近似绕过，数据未对齐时不得声称 100% 复现。

## 异常可观测性硬门禁

- 每个 `try/catch` 都必须在前端或后端留下完整、可检索的异常堆栈日志；无论异常被重抛、转换、降级、返回错误响应还是被最终处理，都不得静默吞掉。
- 日志必须保留原始异常对象或完整 `name`、`message`、`stack`，不能只记录 message、错误码、`String(error)`、摘要或截断堆栈。
- 允许脱敏 token、cookie、密码和业务 payload，但不得删除、覆盖或截断异常堆栈；最终处理边界必须使用项目既有 logger、telemetry 或前端 error reporter 留下完整堆栈，并关联 request/trace 上下文。

## 关键函数注释硬门禁

- 关键函数必须有必要的中文备注，至少说明函数作用；涉及核心规则、状态转换、外部 I/O、异常边界、并发/事务或复杂算法时，还要说明关键前置/后置条件、重要副作用和不能随意修改的约束。
- 中文备注写在函数声明附近，解释“为什么”和边界，不逐行翻译代码、不重复函数名/参数名；简单 getter/setter 和显而易见的转发函数无需强行注释。
- 新增或修改关键函数时，同步更新失效的旧备注；若函数语义无法用简短中文备注准确说明，先拆分职责或澄清合同，不用空泛注释掩盖复杂度。

## 反模式

1. 禁止未定位根因即修补——含加兜底、加timeout、加try-catch吞异常；慢/卡/超时先补证据并二分定位
2. 禁止为避免报错牺牲数据正确性与语义一致性
3. 禁止重复逻辑绕结构问题——该抽抽象就抽，不复制粘贴
4. 禁止顺手无关重构——只改当前目标所需范围
5. 禁止大对象入普通 ref/reactive 后 deep watch 或多层 computed 扫描；禁止对 chat.messages、任务树、metadata 大树做 `{ deep: true, flush: 'sync' }` 监听
6. 禁止用"自动响应式同步一切"替代明确状态边界——大 payload 先定所有权、更新频率、渲染消费点与失效条件，再决定 shallow/raw/lazy 策略
7. 禁止未获授权执行破坏性命令；禁止擅改用户未要求之产品合同
8. 禁止吞错或静默失败——错误须可诊断；禁止层层 fallback 掩异常路径
9. 禁止新增兼容旧行为、fallback 或双路径来掩盖合同迁移；重构必须收敛到目标合同
10. 禁止用系统默认编码写 UTF-8 文本
11. 禁止新增代码无存在理由
12. 禁止非必要网页搜索——先本仓、文档、计划、工具事实
13. 禁止随意新增运行时校验、防御性判断、重复 schema 解析或热路径断言——先证明非法值沿完整链路真实可达、定位唯一边界 owner，并优先复用既有校验点；确实必要时，先请求用户确认，并说明校验位置、触发频率、性能成本和低成本替代方案
14. 禁止把 plugin 入参写成 exact object 合同或 unknown-field rejection——插件提供必要字段即可，额外字段应透传、保留或忽略；不得仅因存在额外字段而拒绝插件、报错或清洗数据
15. 禁止非必要拷贝逻辑——不要顺手使用 spread、map 重建、deepClone、structuredClone、JSON 序列化拷贝或全量对象复制来规避所有权问题；确需拷贝时，只拷贝最小必要字段或最小变更路径，并说明原因、数据规模与热路径影响
16. 禁止新增薄的 adapter、wrapper、mapper、normalizer 或 service facade——如果只是透传调用、改名、同形字段映射、一行函数转发或把类型从 A 包成 A，应删除中间层并直接使用原接口；只有存在真实协议转换、错误语义转换、生命周期隔离、第三方 API 稳定化或跨边界适配时才保留
17. 禁止用全量数据处理掩盖数据流设计问题——不要把完整列表、完整消息树、完整 metadata、完整任务树在多层之间反复传递、filter/map/reduce、normalize 或重建；应按技术方案落实单一数据源、最小载荷、ID/增量传递、消费点派生和局部失效，不能新增运行时校验或拦截器来硬性防止错误流向
18. 禁止为了转换而转换——不要新增只改字段名、换类型名、浅层展开/包回、DTO/VO/Entity/ViewModel/State/Event 同形互转的 mapper/normalizer/serializer；只有真实语义变化、协议变化、持久化模型变化、信任边界变化或消费形态变化时才写转换逻辑
19. 禁止用其他字段组合近似实现缺失字段——如果下游功能需要某个语义字段，必须沿上游数据源、API/事件 payload、类型定义、store/state、测试 fixture 补齐该字段衔接；不得因为上游没传，就用名称、时间、状态、ID、metadata 等字段拼凑推断来冒充该字段
20. 禁止 DataOps AI 语义消费绕过 `NormalizedAgentEvent`——涉及 AI runtime、read-model、工具结果、任务、统计或回放时，只能从 `NormalizedAgentEvent` 明确字段读取语义事实；不得从 raw payload、metadata、activity title/status、session.jsonl、相邻消息、消息顺序或旧字段 fallback 推断
21. 禁止前端跨多组件数据流靠层层转发——Vue 状态跨多个组件、兄弟组件、深层后代或页面模块时，使用 Pinia store 或 provide/inject typed key 承载；React 状态跨多个组件、兄弟组件、深层后代或页面模块时，使用 Zustand store 承载；emit/callback 只表达直接子到父的局部事件，props 只传直接子组件需要的输入，ref/useState/useReducer 只留在组件内部或明确拥有者处
22. 禁止发现本轮改动被撤回或污染后直接覆盖重做——这通常说明有其他线程并发修改；必须先在当前工作目录文件夹根目录的 `mailbox.md` 追加协商信息，说明任务、受影响文件、观察到的撤回/污染、自己的意图和需要对方确认的问题，读完已有消息并协商后再继续；对应协作处理完成后立即删除该消息内容，不写完成标记；不得写到子项目根目录的 `mailbox.md`
23. 禁止重构时留下兼容、fallback 或双路径——重构要一步到位改到目标合同；同步删除旧字段、旧入口、旧分支、旧测试、兼容桥、fallback 逻辑和临时映射，不得用“先兼容以后删”收尾
24. 禁止每完成一个功能点、文件或小编辑就运行测试——先完成架构定义的大阶段全部代码、类型、调用方、迁移、fixture、测试代码、旧路径删除和文档，再交 code-review；复评通过后才由 verification 集中执行测试矩阵
25. 禁止困难排障只靠猜测或测试通过后删除调试日志——遇到难以排除、复现成本高、跨模块、异步、并发、性能或状态流问题时，应增加有信号的调试/诊断日志；这些日志代码作为可维护性代码保留，不因测试通过而清除。日志应优先使用项目既有 logger、级别和稳定标签，记录关键 ID、状态转移、耗时、分支原因或外部调用结果，避免敏感信息、全量大 payload 和热路径无门控刷屏
26. 禁止主动新增 fallback、兜底、降级、回退或备用路径——fallback 会让心智模型和数据流变复杂；只有用户明确提出要加 fallback 时才允许实现。用户未提出时，应修正主路径合同、字段衔接、错误暴露或状态边界，不得用 fallback 掩盖根因、数据缺口或迁移未完成
27. 禁止把浏览器/e2e 测试写成一次性逐步脚本，也禁止为了少写几行制造薄 helper——登录、导航、建数据、等待、截图、控制台采集、通用技术断言只有在至少两个独立稳定合同重复、职责与生命周期稳定时，才复用或沉淀到项目测试 SDK、fixture、page object；业务选择器、业务步骤和业务断言留在测试，临时 Playwright/Browser 步骤只用于探索定位
28. 禁止在多线程并发修改中撤回、覆盖或顺手修改其他线程的改动——发现同一文件存在其他线程改动、自己的改动被对方改写、或需要修改对方正在负责的区域时，先暂停该文件写入，在当前工作目录文件夹根目录 `mailbox.md` 协商；协商期间转去做不冲突的文件或任务，只有达成一致或收到用户指示后再继续改该文件；事项处理完成后立即删除对应消息
29. 禁止不检查更简单实现就编码——同一需求先看能否用更少状态、更短数据路径、更少模块、更少转换、更直接字段衔接实现；不得因为已有技术方案复杂就机械执行。若发现更简单且等价的实现，应回到 architecture-planning 更新方案或说明偏离原因
30. 禁止对象里写意义完全相同的冗余字段——创建或修改 object、payload、state、event、DTO、fixture、mock、配置时，同一语义只保留一个权威字段；不要为了调用方便、兼容旧名或减少改调用方而同时写两套同义字段。处理方式是改字段合同和全链路调用方，不是加运行时校验
31. 禁止把思维链、隐藏推理或思考过程写入产物——创建 HTML、Markdown、PDF/报告、页面文案、代码注释、fixture、snapshot、debug 面板、内嵌 JSON、脚本变量、日志或测试输出时，不得写入 chain-of-thought、scratchpad、内部推理、提示词片段、系统/开发者指令或模型分析过程；只写用户可见的结论、决策、假设、证据和必要理由。处理方式是在生成源头不写入，不是新增运行时扫描、过滤器或校验器
32. 禁止没有测试价值缺口就新增测试——先查已有同合同测试；能扩展、合并或由更高层稳定证明时，不再为本次实现细节新增一份
33. 禁止用源码字符串或正则证明运行时功能——不得因标识符、函数顺序、模板片段、mock 调用或局部 CSS 文本存在就判功能正确；结构规则改用 AST/lint，行为改用实际模块、组件、HTTP 或浏览器结果
34. 禁止白盒和 mock 自证——不得通过 `as any`、`Object.create`、私有方法访问或完整内部 mock 链固化实现；mock 只放技术方案批准的外部边界
35. 禁止新增孤儿测试、伪 E2E 和截图即断言——永久测试必须进入标准 runner；替代目标后端的浏览器测试标 integration；截图必须配 baseline 或稳定视觉合同
36. 禁止把永久测试写成顶层断言或 `main().catch()` 可执行脚本——使用项目已锁定的现代 runner；无第三方 runner 且不能安装依赖时使用语言标准 runner。每个主要失败原因注册独立 test case/suite，生命周期、timeout、mock/spy、隔离与 reporter 使用 runner 原生能力；不得把旧文件整体塞进唯一 `test('main')`，也不得只把 `assert` 批量改成 `expect`
37. 禁止在 async suite callback 中执行 setup 后再 `await test(...)`，或让 case 按顺序共享前一个 case 创建的数据/变量——suite/test 必须同步注册，公共环境只进 runner hook/fixture；每个 case 自备前置数据且按名称单独运行仍成立。不可拆的连续原子事务合并为一个合同 case，不为形式上的 case 数量强拆
38. 禁止用补拉数据掩盖主链路字段缺口——先补齐权威生产者、事件/API、持久化与消费端之间的字段衔接；除非源头无法提供或明确需要跨系统对账，否则不得新增额外查询、轮询或第二数据路径作为补丁

## 产出

代码变更按大阶段任务清单逐条实现，每条完成后只标记实现状态；阶段内不运行验收测试。整个大阶段完成并通过 code-review 后，才进入 verification 集中测试。

实现过程中持续检查心智模型和数据流是否简单：读者应能快速回答数据从哪来、谁拥有、在哪里派生、谁消费、何时失效；若新增状态、转换、事件、缓存、adapter、store、hook 或跨层传递，必须确认它让整体实现更简单而不是更绕。

若任务涉及运行时校验，只能实现已获用户确认的校验；不得为让错误消失或让测试通过临时追加校验。

若任务涉及边界处理，必须在代码或变更说明中标明 source-to-consumer 链路、非法值真实来源、唯一校验/解析/拦截 owner 和下游依赖的合同；上游已排除的非法值不在下游重复处理，也不得为了覆盖理论状态手工制造永久测试。

若任务涉及 plugin 模式，代码只读取必要字段；额外字段处理需与技术方案一致，不能新增阻止插件扩展的严格校验。

若任务涉及拷贝逻辑，代码必须保持最小范围拷贝；不得为避免思考可变性、引用共享或响应式边界而新增全量拷贝。

若任务涉及 adapter，代码必须体现真实适配职责；无法说清职责的薄 adapter 应合并到调用方或被调用方。

若任务涉及数据流，代码必须体现架构上的瘦数据流：跨模块只传必要数据，避免无必要全量扫描、全量重算、全量事件广播和多处缓存同一事实。

若任务涉及转换逻辑，代码必须体现真实语义差异；无法说明差异的同形转换应删除，并让调用方直接使用原模型或在真实边界处做最小转换。

若任务涉及缺失字段，代码必须补齐字段来源和传递链路；同步更新类型、调用方、fixture、测试和文档，不得在消费点写近似推断逻辑。

若任务涉及对象字段，代码必须保持字段语义唯一：同一对象内不得同时存在意义完全相同的字段；字段改名或语义收敛时，一次性更新类型、构造点、消费点、fixture、mock、测试和文档，删除旧同义字段，不添加运行时校验来“防止重复字段”。

若任务会生成、修改或持久化 HTML、Markdown、报告、测试产物、debug 面板、注释、日志或内嵌数据，只允许写入可公开的结论、决策、假设、证据和必要理由；不得把思维链、隐藏推理、scratchpad、提示词片段、系统/开发者指令或模型分析过程写进 DOM、HTML 注释、data 属性、JS 变量、JSON blob、fixture、snapshot 或日志。需要解释时写简短结论说明，不写内部思考过程。

若任务涉及 DataOps AI runtime/read-model/工具结果/任务/统计/回放，语义事实必须来自 `NormalizedAgentEvent` 的显式字段；Pi/session/jsonl/raw payload 只保留运行时或调试证据职责，不得作为语义 fallback。

若任务涉及 Vue 跨组件状态，代码必须避免中间组件只转发 props、emit 或 ref；共享领域状态进 Pinia，局部子树上下文用 provide/inject，并同步类型、测试和组件调用点。

若任务涉及 React 跨组件状态，代码必须避免中间组件只转发 props、callback 或 state；共享领域/应用状态进 Zustand store，组件内部临时状态才用 `useState`/`useReducer`，并同步类型、测试和组件调用点。

若发现自己的任务改动被撤回、被其他改动覆盖、同一文件出现非自己造成的相互污染，先暂停对相关文件继续写入；读取或创建当前工作目录文件夹根目录下的 `mailbox.md`，追加带时间、任务、文件路径、冲突描述、期望处理方式的未决消息，等待协商结果或用户指示；协作处理完成后立即删除对应消息内容，不写完成标记；禁止静默抢写；不得改用子项目根目录的 `mailbox.md`。

若发现其他线程已经修改了同一文件或同一代码区域，不得用 `git checkout`、`git reset`、反向 patch、格式化全文件、重写整段代码等方式撤回或覆盖对方改动；先在 `mailbox.md` 协商文件归属、保留内容和合并方式，协商未完成前只处理无冲突任务。协商完成且文件已释放后立即删除对应消息，不保留“已完成”记录。若没有无冲突任务可做，向用户说明正在等待协商，不要强行继续写冲突文件。

若任务是重构，代码必须只保留重构后的目标路径；调用方、类型、fixture、测试、文档一次性切到新合同，删除所有旧路径兼容和 fallback，不能留下 TODO、临时开关或双写过渡。

若任务需要测试，实现阶段只完成最终目标所需的 Playwright 系统测试代码和入口更新，不执行测试命令。涉及数据库时，复用当前开发数据库，不新增每次测试启动的临时测试库，也不通过 SQL/API 直接构造或断言业务结果。verification 集中测试失败后，回到实现按共同根因修完整批问题并再次通过 code-review，再由 verification 统一重跑受影响系统测试。

新增或修改永久测试时，在测试名或相邻测试结构中清楚表达稳定合同和主要失败原因；只保留最小必要 fixture 与断言，并确认该文件由计划中的标准命令发现。同批改造旧测试时直接删除旧源码契约、重复 fixture 和旧 runner，不保留兼容入口。

若排障过程中新增调试/诊断日志，保留日志代码；最终说明记录日志位置、标签和触发条件，不得在验证通过后作为“清理临时代码”删除。

若用户明确要求 fallback，代码必须把 fallback 与主路径边界写清楚，记录触发条件、数据来源、状态收敛、日志标签和删除成本；用户未明确要求时，禁止以“更稳”“兼容一下”“防止报错”为理由新增 fallback。

若任务涉及测试复用，优先使用项目已有的 Playwright fixture、登录/导航能力和 console/network 健康采集。新增共享能力必须有至少两个当前稳定消费者、明确 owner、技术职责、setup/cleanup 生命周期和退役条件；业务步骤、选择器与断言留在 case 内。禁止 mock/stub、`page.route`、直接 API/SQL、barrel/re-export、巨型默认 fixture 和同形 wrapper。
