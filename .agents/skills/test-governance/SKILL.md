# test-governance

## 最高优先级禁令

以下规则优先于本技能的其他规则，后续条款不得作为例外：

1. **真实用户环境是系统验收最高优先级**：系统验收必须保持用户实际使用的入口、配置、依赖、数据路径和可见结果。测试便利、环境隔离、兼容安排和风险控制与验收真实性冲突时，验收真实性优先；未经用户明确批准，不得改变实际用户路径或用替代环境缩小验收范围。排障证据不能替代系统验收。
2. **禁止过度锁与并发设计**：没有真实并发入口、共享资源及用户/协议合同，不设计锁、队列、worker、并发池或异步编排。
3. **禁止 smoke/冒烟测试**：服务存活、健康检查、页面可打开或元素存在只能用于环境就绪，不能作为测试或验收证据。
4. **禁止内部防御式编程**：不为理论非法状态增加 optional 分支、默认值、吞错、重复校验、过滤、fallback 或兼容路径；真实 ingress 仅由唯一 owner 处理。
5. **谨慎看待竞态，大部分情况下不可能出现竞态**
6. **不预设边界情况**：没有用户反馈、真实使用证据或既有明确合同，不把想象中的边界情况写成设计、代码、测试或结论；先完成主路径，后续按实际反馈处理。

## 用户结果优先于改动规模

- 测试价值按完整用户结果、稳定业务合同和失败风险判断，不按本次 diff 大小或新增文件数量缩减覆盖。
- 一个用户流程跨多个模块时，用真实 UI 路径证明端到端可完成；不能因为某层“只是 UI/绑定”就放弃真实状态、错误和恢复合同。

## 用户体验测试目标

- 系统测试的目标不是证明页面存在或接口返回，而是证明用户体验确有改善：用户能理解界面、完成关键交互、获得预期功能结果，并在失败时知道如何恢复。
- 每个系统测试 case 必须对应一个用户目标和可感知改善；不为单个控件、实现函数或后台调用建立脱离用户体验的通过条件。
- UI、交互和功能的优化必须在同一真实用户路径中成立。仅视觉更精致、步骤更多或功能更多但不能降低用户摩擦的改动不得据此通过验收。

## 正常功能只做系统测试

- 正常功能开发后的正式测试矩阵固定为系统测试一层。系统测试仅使用项目已有的 Playwright，所有业务步骤和断言通过页面 UI 操作完成。
- 系统测试必须联通真实前端、后端和当前开发数据库；必须从用户可见入口完成操作，验证可见结果、刷新后的状态和必要失败恢复。
- 禁止 `page.route`/`context.route`、mock/stub、直接 HTTP/API/SQL、SDK 后门、unit、component、contract、integration、visual、performance、源码静态断言作为正常功能的测试或验收证据。
- 禁止新增、运行或保留 smoke/冒烟测试。进程存活、健康端点、首页可达或元素存在只能作为环境准备检查，不注册为测试 case，也不能计入系统测试、覆盖或通过证据。
- 既有其他层级测试不因正常功能改动而运行、扩展或用作通过条件。只有用户明确要求测试体系迁移、专项测试或故障定位时，才能另行定义范围，且不得把该例外混入正常功能验收。

## 系统测试以功能闭环为单位

- 一个 Playwright 系统测试 case 默认对应一个用户目标：从真实入口开始，完成必要 UI 操作，并看到可解释的成功、失败或恢复结果。连续点击、确认和刷新只要属于同一个目标，就保留在同一个 case 内，不按按钮、请求或函数拆分。
- 页面用例的断言必须是用户可见结果和关键状态转移，例如“打开日志后看到该资源的日志”“断开后该会话消失”“停用后行状态变为已停用”。请求体、调用次数、缓存变量、私有 state、源码字符串、完整 DOM 树和直接接口结果不是系统测试证据。
- 截图只能作为人工取证，不能成为正常功能的视觉测试或通过条件。
- 当一条流程同时覆盖多个实现细节时，优先合并为一条可按名称独立运行的闭环 case；只有失败归因完全不同、用户目标不同或需要不同生命周期时才拆开。

## 测试发现的复杂度回流

- 若真实 UI 路径必须依赖冗长准备、隐蔽调用顺序、多个无语义的状态组合或业务 helper 才能完成，先检查用户流程、业务概念、原语和底层动作的设计；不要把架构问题藏进 fixture、page object 或测试 SDK。
- 只把稳定且至少有两个消费者的通用技术机制抽到测试共享层。测试复杂度反映跨模块边界、状态 owner 或领域动作不清时，退回 `architecture-planning`，而不是增加更多测试封装。
- 不通过直接并发 API/SQL、手工线程或私有 hook 制造 race case。只有产品和架构定义了真实用户可触发的并发合同，才在 Playwright UI 路径验证其可见结果；不要为内部锁、队列、worker 或调度器补算法/时序测试。

## 目标

让少量稳定测试保护真实合同，并能明确回答：什么能力坏了、在哪一层坏、证据是否足以交付。测试数量和覆盖率数字不是目标。

## 开发数据库测试约定

- 当前环境的数据库是可任意修改的开发数据库。系统测试直接复用该库；不得为每次测试、每个 case 或每个测试批次创建、启动或销毁临时测试库、数据库容器或替代连接。
- 系统测试的业务操作和断言只通过 UI 完成。数据生命周期必须可追踪、可清理，且不能借助直接 SQL、后端测试 SDK 或 API 调用绕过 UI。
- 只有用户明确要求隔离数据库环境时，才可规划独立数据库；在此之前，不因“更安全”“方便重置”或单次测试需要引入临时测试库。

## 移动端测试范围

- 用户未明确要求移动端适配、响应式布局或小屏交互时，前端测试默认只覆盖需求指定的目标平台和当前桌面目标视口；不得新增移动端视口、断点、触摸交互或小屏兼容测试。
- 只有用户明确提出移动端或响应式范围时，才在测试矩阵中加入对应的小屏布局、交互和视觉合同；未提出时不以移动端适配缺失作为测试缺口。

## 原型 HTML 复现测试治理

- UI 复现原型 HTML 的视觉测试必须复用原型的 mock 数据或字节等价快照，并记录 fixture/data contract 版本、字段类型和值、顺序、空值/缺失值以及筛选、排序、分页和时间状态。
- 原型和目标 UI 的数据、视口或交互状态不一致时，测试证据只能标记为“不可比”；不得把不同数据的截图差异算作 UI 失败，也不得据此宣称 100% 一致。先对齐唯一 fixture owner 的数据合同，再运行视觉比较。

## mailbox 消息生命周期

- `mailbox.md` 只保存当前未解决、需要协商的消息，不是历史日志、任务清单或完成记录。
- 消息对应的冲突、文件占用或协作事项已处理、完成、释放或经用户确认后，立即删除该消息对应内容；不要追加“已处理”“已完成”“已释放”标记，也不要留下空壳。
- 删除只针对已处理消息，其他线程未处理的内容必须原样保留；一条消息混有已处理和未处理内容时，只删已处理部分，保留未决事项。
- 新增消息前先读取当前内容，避免重复创建；继续协作时只维护未决内容，已删除内容不需要恢复为历史记录。

## 功能模块并行

- 测试设计、迁移、评审或集中执行需要并行时，按独立功能模块或纵向业务合同划分，每个模块仅包含其 Playwright 系统测试证据。
- 禁止按 runner、测试层级、前端/后端、写测试/跑测试/修测试等任务类型拆分并行；这会增加交接、重复 fixture 和证据割裂，不能作为加速依据。
- 每个模块只有一个测试证据 owner，负责测试价值、层级选择、fixture/SDK 复用、失败归因和结果汇总；跨模块公共 runner、环境和共享合同由唯一集成 owner 管理。
- 并行必须服从计划大阶段集中测试门禁。模块内可以准备测试代码，但正式执行仍在整阶段 code-review 通过后统一进入 verification。

## 异常日志测试合同

- 涉及异常处理的测试必须把“完整堆栈已记录”作为稳定合同：断言 logger、telemetry、console error 或 error reporter 收到原始异常对象或包含完整 `stack` 的结构化记录。
- 覆盖主要处理分支及前端 `pageerror`/`unhandledrejection`；不能只断言状态码、错误文案、fallback 结果、message、调用次数或 error 标签。

## 前置盘点

## 关键函数注释测试治理

- 注释要求属于代码可维护性门禁，不为每个函数新增低价值测试；只在 static/lint 规则已有统一入口且能稳定识别关键函数时纳入检查。
- 测试应验证关键函数的行为合同和边界，不能用“存在中文注释”替代运行时测试，也不能为满足注释要求增加源码字符串断言。

## 前置盘点

新增或修改测试前先查：

1. 应用级与仓库级测试命令、runner config、test directories。
2. 已有同合同测试、fixture、helper、SDK、page object，以及当前开发数据库中的数据隔离与清理机制；不得把临时测试库当作默认隔离方案。
3. 测试是否被标准命令发现；是否存在孤儿脚本、重复测试、错误命名层级。
4. 当前改动的稳定合同、真实风险、最小充分证据。
5. runner 是否提供独立 test case、suite、setup/teardown、mock、超时、并发/隔离和结构化 reporter；现有永久测试是否仍是顶层断言或 `main().catch()` 脚本。

## 后端声明式能力证据

- 后端注解/装饰器、schema、模块 metadata 或 DI provider 驱动的能力，运行时合同由真实框架装配、metadata discovery、DI 生命周期和公开 handler/API 结果证明；源码中出现 `@Decorator`、私有 metadata 快照或完整 discovery mock 链不是有效行为证据。
- 不为声明式能力额外运行 static、contract 或 integration 测试；注册、权限、事务、校验、序列化和失败清理由同一条真实 UI 系统路径验证。
- 扩展 fixture 可定义最小带注解 provider/handler，但业务断言留在测试；不得为测试创建第二套 registry、扫描器、命名约定或兼容装配路径。测试应证明声明是唯一事实源，而不是与中央列表双写。

## 链路边界与测试 Owner

- 测试边界前先沿 `source -> transport/API/event -> schema/parser -> service/use case -> persistence/state -> consumer` 判断值是否真实可达，明确首次拥有边界的层和下游依赖的合同；不能从局部函数“理论可传入”推出生产边界。
- 系统测试以真实 UI 入口和完整结果为准，不能通过下游 fixture、强制类型、私有调用或手工改状态制造上游不可能产生的非法输入；这类失败先判定为测试构造失真，不据此新增生产防御。
- 用户/外部协议、历史数据库、插件/第三方、跨信任域和不可信序列化属于真实 ingress boundary。上游 schema、类型、解析器或框架装配已排除的非法值，不在下游手工注入，不新增永久测试，也不以此要求运行时拦截。
- 同一边界只保留一个权威系统测试 owner，通过真实 UI 入口验证拒绝/转换及下游消费；不复制 controller/service/store/consumer 的相同 invalid-value case，也不新增 contract/integration 测试。
- 若存在绕过既有 owner 的真实入口，应在该入口补测试，并记录输入/输出合同、失败语义和下游假设。static/AST 只能证明结构规则，不能替代可达性或运行时边界证据。
- 不为内部哈希、校验和、指纹、内容比对或理论碰撞编写系统测试；只有真实安全、协议、内容寻址或幂等合同经 UI 路径产生用户可观察结果时，才覆盖该合同，不测试私有算法细节或下游重复计算。
- 不为防御式编程写系统测试：不测试内部 optional 分支、默认值、吞错、重复校验、过滤或 fallback。只经真实 UI 入口覆盖其唯一边界 owner 的用户可见结果，测试构造的内部异常状态一律删除。

## 计划大阶段测试节奏

- “集中测试”的单位是 architecture-planning 在计划文档中预先定义的一个大阶段，不是一次 implementation、一个功能点、一个文件或一个临时批次。一个大阶段可以包含多轮实现、多个任务和多次内部调整。
- 阶段内可以持续编写、迁移和自查测试代码、fixture、SDK 与 runner 配置，但不进入正式 code-review、不执行正式测试命令。只有该计划阶段全部生产代码、调用方、迁移、测试和文档完成后才做整阶段 code-review，复评通过后才进入 verification。
- 每个计划大阶段只设置一个集中测试阶段，按预先定义的矩阵统一运行相关层级。禁止在任务清单每个功能点后附 test command，禁止形成“实现一点 -> 评审一次 -> 测试一次”的循环。
- 实现被阻塞时允许一次最小诊断命令或探针；集中测试失败后允许按名称过滤定位根因。这些命令不构成功能验收，最终证据必须回到整阶段矩阵。
- 集中测试失败时先完成整轮证据收集并按共同根因分组，再整批返回 implementation；关联问题全部修复并通过整阶段复评后，统一重跑受影响矩阵，不每修一个 case 就运行一次。

## 测试价值门禁

永久测试必须同时满足：

- **稳定合同**：保护用户结果、业务规则、公共 API/event/schema、状态转移、持久化、权限或明确架构边界。
- **真实故障**：能描述一个生产代码可能发生、且该测试会捕获的故障。
- **充分证据**：断言证明合同结果，不只证明实现中存在某段文字、某个 mock 调用或某个私有函数。
- **主要失败原因**：失败时主要指向一个合同；不要把多个无关业务目标绑成长流程。
- **标准入口**：由 package/root aggregate 命令发现；禁止未注册的永久 `node xxx.test.*` 脚本。
- **现代 runner**：永久测试必须注册为 runner 原生 test case/suite，并使用其生命周期、超时、mock/spy、隔离和结构化报告能力；禁止把顶层 `assert`、`main().catch()`、自建逐文件子进程或日志中的 `[PASS]` 当测试框架。
- **无重复**：优先扩展、合并或替换已有测试；同批迁移删除旧测试，不保留双路径。

不满足门禁时不新增测试；若现有测试不满足，改造或删除。

## Runner 基线

- 正常功能测试只使用项目已经锁定并安装的 Playwright 命令与配置。不得跨 package 借用依赖、临时调用其他 runner，或因缺少 Playwright 改用 Vitest、Jest、pytest、Node.js `node:test` 等替代。
- 一个稳定合同或一个主要失败原因对应可独立命名、过滤、超时和报告的 test case；相关 case 可用 suite 分组，但不得把整个文件包装成唯一 `test('main')` 来形式化迁移。
- suite/test 必须在 runner 收集阶段同步注册；禁止在 async suite callback 中先执行 setup 再 `await test(...)`，也禁止用自建循环顺序运行 case。公共环境放 `before/after/beforeEach/afterEach` 或 fixture。
- 每个 case 必须自备或由 hook 获得前置数据，不得依赖兄弟 case 已执行、已创建数据、已修改共享变量或执行顺序；用名称过滤只运行该 case 时仍须成立。确实不可拆的连续原子业务事务应作为一个合同 case，而不是伪拆成相互依赖的步骤。
- setup/teardown、临时目录、环境恢复、fake timer 和资源释放使用 runner hook/fixture；禁止每个 case 手写重复生命周期或靠进程退出清理。
- runner 迁移不能替代测试价值治理。迁移前先删除源码字符串、白盒、mock 自证、重复排列和伪层级，再把保留合同迁为原生 case；禁止只把 `assert` 批量替换成 `expect`。

## 测试层级

正常功能的唯一层级是系统测试：项目 Playwright 通过 UI 操作真实前端、后端和开发数据库，并以可见结果、状态刷新及失败恢复作为证据。不要新增或运行其他测试层级，也不要把一个用户目标拆成私有实现断言。

## 证据边界

- 源码字符串、正则、标识符、函数顺序、模板片段和普通局部 CSS 数值不能证明运行时行为。仅模块边界、依赖方向、禁用 API 等规则可用 AST/lint/static test。
- 禁止 mock/stub、`page.route`、`as any`、私有访问、直接 API/SQL 或后端测试 SDK。系统测试只保留真实 UI 到前后端的用户路径。
- 测试不得用 fallback、兼容路径、近似字段、额外拷贝、薄 adapter 或新增运行时校验让结果通过。

## Playwright 系统测试

- 使用 `page.route`/`context.route`、mock/stub 或 backend-only 调用的用例不是系统测试，正常功能不得新增或运行。
- 系统测试必须复用真实 frontend/backend、当前开发数据库和真实浏览器路径；不得用 backend-only 调用替代用户路径。
- console/network health 通过项目 fixture/SDK 统一采集：`console error/warn`、`pageerror`、`requestfailed`、意外 `4xx/5xx`、CORS、资源失败、关键请求与长时间 pending。
- `page.screenshot()` 仅能人工取证，不能成为系统测试断言或替代 UI 操作。

## 响应式更新测试

- 系统测试优先通过用户操作或真实服务端事件等待可观察 UI 状态更新；禁止用测试内轮询、固定 `waitForTimeout`、反复刷新或持续请求把异步状态“等出来”。
- 涉及订阅、WebSocket/SSE 或后端事件时，验证一次真实变化是否使正确 UI 消费者更新，并检查离开页面、断线或取消后不再产生过期更新。
- 允许轮询的外部系统必须有架构阶段批准；系统测试只验证其退避、上限、取消、停止和用户可见等待/失败状态，不把无限定时刷新固化为合同。
- 固定 sleep 不得用于等待业务状态、实现测试轮询或替代页面同步；仅可模拟有明确时序合同的协议时间线。页面同步必须等待可观察状态或目标请求。

## 断线恢复测试合同

- 涉及上游运行时断线时，系统测试从真实 UI 触发断开和重新连接，验证恢复后的状态来自上游权威持久事实源的原生游标增量读取，并能继续显示新的实时更新；不得用测试夹具、直接接口或自建 replay 队列伪造恢复。
- 只把上游已持久化事实作为恢复断言。未持久化的 token delta 或临时进度允许丢失，不写成“必须逐条补回”的合同；验证未知命令在断线后未被自动重发。
- 若上游没有持久事实源、稳定游标或已定义的增量恢复协议，测试治理必须退回 architecture-planning 明确恢复合同，不用事件 buffer、journal、outbox 或补偿 watcher 让测试表面通过。

## Fixture、Helper 与 SDK 复用规范

复用目标是减少稳定技术机制的重复生命周期和错误处理，不是减少测试文件行数，也不是把业务流程藏进公共层。

### 抽取门槛

共享能力必须同时满足：

1. 已在至少两个独立稳定合同中重复；首次或仍在探索的流程留在测试内。
2. 重复的是环境、认证、隔离数据、清理、协议模拟、诊断采集或通用技术断言，不是业务判断。
3. 参数、返回值、资源所有权和 setup/cleanup 生命周期稳定。
4. 抽取后减少真实重复和失败分支；若只是少写几行调用、转发参数或改名，不抽取。
5. 有当前直接消费者；禁止为未来可能复用预建 helper、factory、page object 或 SDK。

### 所有权与目录

- runner 级 setup 放 runner config 或专用 setup 文件，不在每个测试重复。
- 同一 runner 的通用技术能力放该测试根的 `support/`；浏览器能力只放 Playwright 系统测试的 `support/`。
- 固定协议样本、文件样本和最小数据集放 `fixtures/`；动态资源创建/清理属于 support/SDK，不把完整生产 payload 复制成 fixture。
- 领域 SDK 只有在同一领域存在多项稳定技术操作和统一资源生命周期时成立；使用明确领域名，禁止无边界的 `test-utils`、`common`、`helpers` 大杂烩。
- 共享模块只有一个权威实现；消费者直接导入，不加 barrel、re-export、兼容路径或同形 wrapper。

### 职责边界

- **允许共享**：环境解析、认证安装、隔离数据创建/清理、时钟/随机/外部协议模拟、console/network/pageerror 采集、资源释放和通用技术健康断言。
- **留在测试**：业务输入、业务选择器、业务状态转移、权限期望、业务错误语义、用户可见结果和场景特有噪声判定。
- support 可以验证自身技术前置条件，例如登录请求成功或清理完成；不得替测试断言目标业务成功。
- fixture/factory 默认只生成合同必要字段；调用点显式提供会影响断言的字段。不得隐藏巨型默认对象、同义字段、近似字段或额外拷贝。
- plugin fixture 只要求必要字段并允许额外字段；不得用 exact-object helper 拒绝插件扩展字段。
- support 返回原始可观察证据或明确技术结果，不转换成预设业务结论。

### 生命周期与退役

- 创建外部资源的共享能力必须在同一 API 暴露对应 cleanup，并由 fixture/runner 保证失败路径也释放。
- 在当前开发数据库中创建或修改数据的共享能力，必须通过同一生命周期提供清理；不得把新建、启动或销毁临时测试库包装为通用测试能力。
- 浏览器统一诊断至少覆盖 console error/warn、pageerror、requestfailed、意外 4xx/5xx、CORS、资源失败和关键长 pending；领域 SDK 只在其上增加领域协议观测，不重复注册通用监听。
- 评审时列出共享能力 owner、直接消费者、承担职责和不承担职责；无法说明者内联或删除。
- 消费者只剩一个、合同分化、runner 已原生提供等价能力，或共享层开始积累业务分支时，删除共享层并把必要逻辑放回明确 owner。
- 禁止复用源码读取/正则、私有访问、完整内部 mock 链、固定 sleep、截图即断言等无效证据；包装后仍是无效测试。

## 既有测试迁移

既有测试治理必须纳入 architecture-planning 定义的计划大阶段；阶段内可按无冲突业务合同安排实现顺序，但不为这些内部批次分别运行测试：

1. 记录旧测试保护的合同与实际证据。
2. 判定保留、合并、改层或删除。
3. 写目标 runner 原生 test case 并接入标准入口；按稳定合同拆 case，不把旧脚本整体包进单一 case。
4. 同批删除旧源码契约、重复 fixture、旧 runner 和错误命名。
5. 所属计划大阶段的全部迁移任务和整阶段 code-review 完成后，在 verification 集中运行目标层及必要上层测试。

每个计划大阶段一步到目标形态，不保留兼容 runner、双测试或 fallback。现有坏模式不得作为新增测试先例。

## 阶段产出

- **产品阶段**：可观察验收标准、风险与关键路径。
- **架构阶段**：定义计划大阶段边界和唯一集中系统测试门禁；列出项目 Playwright 命令、真实前后端边界、开发数据库生命周期和用户路径，不得为每个功能点安排测试命令或临时测试库。
- **实现阶段**：在大阶段内完成最小 Playwright 系统测试变更与旧测试删除；复用既有 UI fixture/诊断能力，不创建 mock、直调 API/SQL 或临时数据库，但不执行正式测试。
- **评审阶段**：只在整个计划大阶段完成后，统一评审系统测试的 UI 路径、真实联调、case 粒度、入口、重复和开发数据库复用；不在每个 finding 修复后运行测试。
- **验证阶段**：整阶段评审通过后集中运行 Playwright 系统测试，产出 UI 操作、可见结果、console/network 健康、失败分组和残余风险；直接复用当前开发数据库，不得临时发明其他测试层级或临时测试库。
