# code-review

## 最高优先级禁令

以下规则优先于本技能的其他规则，后续条款不得作为例外：

1. **禁止过度锁与并发设计**：没有真实并发入口、共享资源及用户/协议合同，不设计锁、队列、worker、并发池或异步编排。
2. **禁止 smoke/冒烟测试**：服务存活、健康检查、页面可打开或元素存在只能用于环境就绪，不能作为测试或验收证据。
3. **禁止内部防御式编程**：不为理论非法状态增加 optional 分支、默认值、吞错、重复校验、过滤、fallback 或兼容路径；真实 ingress 仅由唯一 owner 处理。
4. **谨慎看待竞态，大部分情况下不可能出现竞态**
5. **不预设边界情况**：没有用户反馈、真实使用证据或既有明确合同，不把想象中的边界情况写成设计、代码、测试或结论；先完成主路径，后续按实际反馈处理。

## 用户体验闭环审查

- 评审不能把“小范围 diff”当作质量目标。若实现只完成视觉入口而没有真实操作、状态反馈、错误恢复或持久化闭环，应退回补齐必要链路。
- 审查用户从入口到结果的心智流是否单一、可发现、可解释；必要的跨模块改动应视为同一功能阶段的一部分，而不是无关扩张。

## 用户体验评审目标

- 评审以用户体验改善为通过条件：UI 是否让信息和下一步更清楚，交互是否减少操作摩擦，功能是否真正帮助用户完成目标。
- 拒绝只增加视觉复杂度、交互步骤、功能开关或技术结构却没有可感知用户收益的改动；也拒绝因实现方便而牺牲主路径可发现性、反馈、恢复或结果确定性。
- 对关键变更追问其用户阻碍、预期改善和可观察结果；三者不能闭环时退回 implementation 或 architecture-planning 收敛。

## 局部复杂度回溯评审

- 发现深层分支、多个状态旗标、调用方编排底层动作、难以解释的转换/抽象或业务规则散落时，不能只要求函数提取或补注释；要求重新审查业务概念封装、原语/动作语义、模块边界和数据 owner。
- 判断设计模式是否真正隔离了变化或状态，而非新增跳转和命名负担。复杂度根因跨模块时，退回 `architecture-planning` 更新方案；仅局部实现问题才在 `implementation` 收敛。

## 运行时并发与锁评审

- 新增 mutex、lock、semaphore、队列、worker、并发池、并发扇出或自定义调度时，要求证明真实并发入口、共享可变资源和用户/协议一致性需求；“未来可能并发”或“保险”不接受。
- 优先要求以所有权、单写者、分区、顺序流程或既有事务收敛。锁必须有单一 owner、最小临界区和明确释放/取消语义；多锁、跨层锁或用锁掩盖状态 owner 不清，一律退回架构重审。

## 系统测试审查

- 正常功能测试必须是项目已有 Playwright 的系统测试，以用户目标闭环为单位，真实驱动前端、后端和当前开发数据库。发现 unit、component、contract、API 直调、mock、`page.route`、截图基线或白盒断言时，要求删除，不转移到另一测试层级。
- 评审优先看“用户操作后是否看到正确结果、刷新后状态是否一致、失败后能否恢复”，而不是断言数量或测试行数。
- 发现 smoke/冒烟测试，或仅验证服务存活、页面可打开和元素存在的“通过”脚本时，要求删除；环境就绪检查不能作为功能测试或评审证据。

## 前置

- 代码变更（来自 implementation）
- 变更涉及测试时，读取并遵守 `test-governance` 及技术方案中的测试矩阵

## 路径口径

- 本技能中的“根目录/当前根目录”指本轮任务开始时探测到的当前工作目录文件夹根目录（`pwd` 对应的工作区根目录），不是该工作目录下某个子项目、子仓库或模块的项目根目录；例如当前工作目录为 `/root/projects` 时，根目录就是 `/root/projects`，不是 `/root/projects/dataops`。

## mailbox 消息生命周期

- `mailbox.md` 只保存当前未解决、需要协商的消息，不是历史日志、任务清单或完成记录。
- 消息对应的冲突、文件占用或协作事项已处理、完成、释放或经用户确认后，立即删除该消息对应内容；不要追加“已处理”“已完成”“已释放”标记，也不要留下空壳。
- 删除只针对已处理消息，其他线程未处理的内容必须原样保留；一条消息混有已处理和未处理内容时，只删已处理部分，保留未决事项。
- 新增消息前先读取当前内容，避免重复创建；继续协作时只维护未决内容，已删除内容不需要恢复为历史记录。

## 功能模块并行

- 整个计划大阶段完成后，如需并行评审，只按已实现的独立功能模块或纵向业务切片分配；每个评审单元覆盖该模块从入口、合同、实现、持久化到测试代码和文档的完整链路。
- 禁止按“安全评审、性能评审、测试评审、前端评审、后端评审”等任务类型拆给不同线程后各看局部；专项维度由模块评审者在模块内统一检查，最后再做跨模块集成复评。
- 检查实现阶段的并行拆分是否确实减少关键路径，是否有单一模块 owner、清晰文件归属和稳定模块合同；发现同一功能被多线程分段交接、共享文件抢写或强依赖伪并行时，要求收敛模块边界。

## 后端声明式评审

- 后端框架已有声明式 API、注解/装饰器和 DI 能力时，若路由、权限、校验、事务、序列化、事件/任务/插件注册仍依赖散落命令式 wiring、中央 `switch`、手工 registry、文件名约定或源码扫描，视为架构问题。
- 扩展功能应由公开 provider/interface 合同、框架可发现注解和所属模块装配完成。检查新增扩展是否主要修改自身实现，是否还要求同步修改无关中央列表，是否存在声明与命令式注册双写。
- 检查声明是否真正参与框架装配、metadata discovery、DI 生命周期和跨切面链，而不是无效标签、薄 wrapper 或只改名的装饰器/DSL；检查目标、参数类型、发现范围、冲突/优先级、实例作用域和启动失败语义。
- 注解、schema hook 或 metadata resolver 不得隐藏 I/O、领域流程、fallback、异常吞噬或绕过 DI。复杂业务流程应保持显式、可读、可组合。
- 运行时能力必须由真实模块装配、公开 API 或可观察 handler 结果证明；源码中存在 `@Decorator`、私有 metadata 快照或完整 discovery mock 链不是有效证据。

## 链路边界评审

- 沿 `source -> transport/API/event -> schema/parser -> service/use case -> persistence/state -> consumer` 追踪每个新增校验、解析、归一化、拦截和错误分支，确认它对应真实可达输入，而不是局部函数的理论输入。
- 审查局部防御的整体代价：没有真实来源和可达路径的 `undefined` 分支、默认值、吞错、类型扩张、拷贝或重复解析，应要求删除；它们会掩盖 owner 处的合同破坏，并增加维护与热路径成本。
- 区分真实边界（用户/外部协议、历史持久化、插件/第三方、跨信任域、不可信序列化）与上游合同已经排除的不可达状态。上游已保证不可达时，要求删除下游重复分支和只为覆盖它而写的测试。
- 检查同一边界是否只有一个 owner，并核对 owner 的输入/输出合同、失败语义和下游假设；重点查重复 schema parse、normalize、validator、interceptor、权限/状态拦截和同义 fallback。
- 发现新增运行时校验或拦截时，必须要求作者说明非法值来源、首次边界 owner、已有 owner 为什么不能承担、热路径成本和数据流分叉风险；未获用户确认或无法证明可达性时不接受。
- 审查新增 hash、checksum、fingerprint、内容比对或碰撞处理时，要求给出真实安全、协议、内容寻址或幂等合同及唯一 owner；“更安全”“防重复”或理论碰撞不是充分理由。内部链路的重复计算和下游哈希防御应删除。
- 把内部 optional 分支、默认值、吞错、重复校验、过滤、fallback 和兼容路径视为防御式编程并默认要求删除；只有能证明真实 ingress 与唯一 owner 的处理才接受，不能用“更稳”替代可达性证据。

## 状态更新评审

- 评审新增定时器、轮询、递归请求、重复 fetch 和多处刷新时，先要求证明没有用户响应、事件、WebSocket/SSE、订阅或共享状态可替代；未证明则改为响应式状态链路。
- 轮询例外必须具备外部限制、退避、频率/总时限上限、并发保护、取消与卸载清理、错误呈现和停止条件；缺任一项不通过。
- 检查事件与订阅是否有唯一 owner、正确清理、去重/顺序语义和断线恢复，避免 UI 已离开后仍写状态或同一变化被多次渲染。

## 断线恢复评审

- 审查每个断线恢复实现是否先使用上游的权威持久事实源、稳定原生游标及其增量读取/订阅合同。上游具备这些能力时，代码只能从最后确认的原生游标补读、在适配边界投影并恢复实时订阅；本地游标不得成为第二份事实记录。
- 发现为传输断开新增事件缓冲、journal、replay 队列、outbox、补偿 watcher、断线熔断/停任务或自动命令重试，默认要求删除。未持久化的流式片段和临时进度不能纳入恢复承诺；未知命令执行结果不得猜测后重发。
- 上游缺少原生恢复能力时，确认实现已停在明确边界并有经过批准的恢复合同；不得以“更可靠”为由默认补建缓冲或重放机制。

## 计划大阶段评审门禁

- 正式 code-review 的输入是计划文档中一个已完成的大阶段，不是一次实现动作、一个功能点、一个文件或一个临时批次。一个计划大阶段可以包含多轮 implementation、多个任务和多次内部调整；阶段未全部完成前不进入正式评审。
- 进入评审前必须确认该计划阶段的生产代码、类型、调用方、迁移、fixture、测试代码、旧路径删除和文档均已完成。缺项时退回 implementation 继续该阶段，不为已完成的局部功能点单独评审和测试。
- 评审覆盖整个计划阶段，问题按共同模块和根因集中修复；修复期间不对每个 finding 运行测试。全部评审问题修完后统一复评代码。
- code-review 不执行阶段验收测试。整阶段复评通过后只做一次移交，由 verification 按计划矩阵集中测试；不能形成“实现一点 -> 评审一次 -> 测试一次”的循环。
- verification 若发现失败，按共同根因退回 implementation 修完整批问题，再对修复后的整阶段做复评；不得围绕单个 case 往返评审。

## 开发数据库测试评审

- 评审涉及数据库的测试改动时，确认测试默认复用当前可任意修改的开发数据库，而非为单个测试、case 或测试批次创建、启动或销毁临时测试库。
- 检查 Playwright case 的业务步骤和断言是否只经 UI 操作完成；测试数据必须可辨识、可清理，且任何 case 不依赖兄弟 case 预先写入的数据、直接 SQL 或后端测试 API。
- 未经用户明确要求隔离环境，发现新增临时数据库配置、数据库容器或按测试切换连接的实现时，评审不通过并退回 implementation 收敛。

## 移动端评审范围

- 用户未明确要求移动端适配、响应式布局或小屏交互时，不因缺少移动端页面、断点、触摸交互或移动端视口测试而阻塞评审；评审以需求指定的目标平台和当前桌面目标为准。
- 发现未被用户要求的移动端专属实现、响应式扩展或小屏测试时，按超出范围处理并要求回到 implementation 删除或取得明确授权；只有用户明确提出后才评审其移动端合同。

## 原型复现评审

- 评审原型 HTML 复现时，必须检查原型与目标 UI 是否使用同一 mock 数据快照、版本、字段类型和值、顺序、空值/缺失值及交互状态，并确认比较视口一致。
- 目标 UI 使用不同数据时，比较结论标记为“不可比”；不得接受以不同数据得到的 100% 一致声明，也不得要求通过 CSS 或 fallback 掩盖数据合同差异，应退回 implementation 对齐数据。

## 异常可观测性硬门禁

- 发现任何 `try/catch`、Promise rejection、全局错误边界或异常转换时，必须确认前端或后端已记录原始异常的完整 `stack`；只记录 message、错误码、`String(error)` 或返回通用错误视为吞错，评审不通过。
- 检查重抛、转换、降级、响应封装和最终消费各路径均不丢失堆栈；允许脱敏敏感上下文，但不允许脱敏、截断或覆盖 `name`、`message`、`stack`。

## 关键函数注释评审门禁

- 评审必须识别跨模块入口、核心规则、状态转换、外部 I/O、异常边界、并发/事务协调和复杂算法等关键函数，确认函数附近有必要的中文备注并准确说明作用与边界。
- 备注缺失、过时、只重复函数名/参数名、逐行翻译代码或用空泛文字掩盖复杂逻辑时，评审不通过；简单 getter/setter 和显而易见的转发函数不要求注释。

## 反模式

1. 禁止只看表面不看结构——评审须覆盖：命名一致性、模块边界遵守、反模式违反、冗余逻辑、死代码
2. 禁止产出无具体修复建议的问题——每个问题必须附带"改哪里、改成什么"
3. 禁止评审顺手加无关改动——修完评审发现的问题即停，不顺手重构
4. 禁止跳过复评——边审边修后必须复评，复评确认无遗留才通过
5. 禁止把一次实现动作对应成一次评审和一次测试——只有计划中的整个大阶段完成后才正式评审；评审阶段集中修完并复评全部问题，不运行阶段验收测试，复评通过后统一交给 verification
6. 禁止把新增拷贝逻辑视为无风险改动——发现 spread/map 重建、deepClone、structuredClone、JSON 序列化拷贝或大对象复制时，必须追问必要性、数据规模、触发频率和热路径影响
7. 禁止放过薄 adapter——发现只透传、改名、同形映射、一行转发的 adapter/wrapper/mapper/normalizer/facade 时，必须要求说明真实适配职责；说不清则删除或合并
8. 禁止把冗余数据流当作实现细节放过——发现全量对象跨层传递、全量列表反复扫描、多处缓存同一事实、事件 payload 过大或派生数据提前下发时，必须要求回到数据所有权、最小载荷、增量处理和消费点派生上修正
9. 禁止放过形式主义转换——发现 DTO/VO/Entity/ViewModel/State/Event 之间只是改名、同形映射、展开后包回或多段 mapper 串联时，必须要求说明真实语义差异；说不清则删除或内联到真实边界
10. 禁止放过字段近似实现——发现下游用多个现有字段拼凑、推断、猜测本应由上游提供的语义字段时，必须要求补齐字段合同和数据流衔接；不能接受“上游没传所以先近似”的实现
11. 禁止放过 DataOps AI 语义事实源旁路——发现 AI runtime/read-model/工具结果/任务/统计/回放从 raw payload、metadata、activity title/status、session.jsonl、相邻消息、消息顺序或旧字段推断语义时，必须要求改为 `NormalizedAgentEvent` 显式字段并删除 fallback
12. 禁止放过前端跨组件状态 drilling——Vue 中发现多个中间组件只负责转发 props、emit、ref 或事件回调时，必须要求改为 Pinia 或 provide/inject；React 中发现多个中间组件只负责转发 props、callback、state 或 setter 时，必须要求改为 Zustand；仅直接父子局部通信可保留 props/emit/callback
13. 禁止放过重构遗留兼容和 fallback——发现旧字段、旧入口、旧分支、兼容桥、fallback、双写、临时开关、旧测试仍存在时，必须要求一次性删除并把调用方切到新合同
14. 禁止把困难排障新增的调试/诊断日志当临时代码删除——测试通过不是删除日志的理由；评审应检查日志是否有信号、稳定标签、合适级别、关键上下文、敏感信息规避和热路径门控，只有无信息量、泄密或明显刷屏的日志才要求调整
15. 禁止放过用户未明确要求的 fallback——发现兜底、降级、回退、备用路径、默认替代数据或失败后改走另一条路径时，必须要求提供用户明确要求记录；没有记录则删除并回到主路径合同、字段衔接、错误暴露或状态边界修正
16. 禁止放过一次性浏览器/e2e 脚本或过度抽象测试 support——重复技术步骤满足至少两个独立稳定合同、职责和生命周期稳定时才复用；发现无第二消费者、只转发/改名、隐藏业务断言、巨型默认 fixture、兼容导出或重复 SDK 时，要求内联、合并或删除
17. 禁止评审时撤回或改写其他线程改动——发现 diff 中有非本任务、非自己造成或疑似其他线程正在处理的改动时，不得为了“修干净”而删除、格式化、重排或重写；先在当前工作目录文件夹根目录 `mailbox.md` 协商，评审期间转向无冲突文件或问题；协作处理完成后立即删除对应消息，不写完成标记
18. 禁止只审正确性不审简单性——即使功能通过，也必须检查同一需求是否有更简单实现；发现心智模型更绕、数据流更长、状态更多、转换更多、模块更多或测试边界更模糊时，要求回到更简单的数据所有权、字段衔接和消费点派生
19. 禁止放过对象内同义冗余字段——发现同一 object、payload、state、event、DTO、fixture、mock 或配置中存在意义完全相同的字段时，必须要求收敛为一个权威字段并同步全链路调用方；不得接受用运行时校验、字段过滤或双写兼容来掩盖
20. 禁止放过产物中的思维链或隐藏推理泄露——评审 HTML、Markdown、报告、页面文案、注释、fixture、snapshot、debug 面板、内嵌 JSON、脚本变量、日志和测试输出时，发现 chain-of-thought、scratchpad、内部推理、思考过程、提示词片段、系统/开发者指令或模型分析过程必须要求删除或改写为结论、决策、假设、证据和必要理由；不得接受新增运行时扫描、过滤或校验来掩盖源头写入问题
21. 禁止只看测试是否通过——每个新增或修改的正常功能测试必须说明稳定合同、真实故障、主要失败原因、真实前后端边界和 Playwright 入口；说不清则删除或改写
22. 禁止放过源码字符串行为测试——标识符、函数顺序、模板片段、mock 调用和局部 CSS 文本不能作为运行时功能证据；仅明确架构边界可用 AST/lint/static test
23. 禁止放过白盒、mock 自证和过量 fixture——发现 `as any`、`Object.create`、私有访问、完整内部 mock 链或远超合同所需的数据时，要求改为公共合同和最小 fixture
24. 禁止放过孤儿测试、错误层级和重复覆盖——测试必须进入标准 Playwright 命令；`page.route`、直接 API/SQL 或 mock 不得称系统测试；同合同重复测试应合并，迁移后旧测试与旧 runner 必须删除
25. 禁止把截图当视觉回归——单独 `page.screenshot()` 只能作证据；无 baseline 或明确布局、溢出、重叠、可访问性合同则不能声称视觉回归已覆盖
26. 禁止放过测试粒度失控——一个测试应有一个主要失败原因；发现按私有函数机械拆分或把多个无关业务合同塞进超长流程时，要求按稳定业务合同重组
27. 禁止接受脚本式永久测试和形式主义框架迁移——顶层 assert、`main().catch()`、逐文件子进程、`[PASS]` 日志不是现代测试管理；测试必须是 runner 原生独立 case/suite，并使用 hook、timeout、mock/spy、隔离、过滤和结构化 reporter。若只是把旧脚本整体包成一个 case 或把 assert 换成 expect，评审不通过
28. 禁止把不可达的理论边界当作实现缺陷——没有真实来源或已被上游合同排除的非法值，不接受下游重复校验、重复拦截或永久测试；同一可达边界必须能指出唯一 owner

## 评审范围

按优先级逐项检查：

1. **反模式违反**——对照 implementation 技能的反模式清单，逐条检查本次变更
2. **架构一致性**——是否符合技术方案中的模块边界、数据流、hook/plugin/reducer 设计
3. **命名与重复**——同概念是否同命名、是否存在可合并的重复逻辑
4. **合同同步**——跨模块接口变更是否已同步调用方、类型、文档
5. **边界与错误**——新增分支是否有真实可达来源，是否已由上游合同处理，是否造成同一边界重复校验/拦截；并发和异常也要按完整链路判断
6. **拷贝逻辑**——是否存在非必要拷贝、全量深拷贝、热路径重复拷贝；能否改为明确所有权、只读合同、局部更新或最小字段投影
7. **Adapter 必要性**——是否存在薄 adapter、无语义 wrapper、同形 mapper、只换名 facade；能否直接调用原接口或把少量转换内联到真正拥有该语义的模块
8. **数据流效率**——是否存在不合理冗余数据流动、全量处理、重复 normalize、重复缓存、过大事件载荷；是否已用单一数据源、ID/增量传递、局部派生和明确失效边界替代
9. **转换必要性**——转换是否改变语义、协议、持久化模型、信任边界或消费形态；是否只是为了分层命名而转换
10. **字段衔接**——功能依赖的语义字段是否从源头传到消费点；是否存在用名称/状态/时间/ID/metadata 等字段组合近似替代缺失字段；类型、fixture、测试、文档是否同步
11. **DataOps AI 事实源**——AI runtime/read-model/工具结果/任务/统计/回放是否只从 `NormalizedAgentEvent` 显式字段读取语义事实；是否已删除 raw payload、metadata、session.jsonl、相邻消息、消息顺序和旧字段 fallback
12. **前端状态管理**——Vue 跨多个组件、兄弟组件、深层后代或页面模块的数据是否进 Pinia 或 provide/inject；React 跨多个组件、兄弟组件、深层后代或页面模块的数据是否进 Zustand；是否存在只转发不消费的中间组件、链式 emit/callback、跨层 ref/state 共享
13. **重构收敛**——是否只保留目标实现；是否已删除兼容层、fallback、旧合同、旧测试、双路径和临时 TODO；调用方是否全部切换完成
14. **诊断日志**——难定位问题是否留下可维护的调试/诊断日志；日志是否使用项目 logger、稳定标签和合适级别，是否避免敏感信息、全量大 payload 和热路径无门控输出
15. **Fallback 控制**——是否新增用户未明确要求的 fallback、兜底、降级、回退、备用路径或默认替代数据；若用户要求 fallback，是否说明触发条件、状态收敛、数据流分叉和删除成本
16. **测试 SDK 复用**——是否优先使用 runner 原生能力和唯一既有 support；共享能力是否有 owner、至少两个稳定消费者、技术职责、setup/cleanup 生命周期和退役条件；业务输入、选择器、步骤与断言是否仍由测试拥有
17. **并发协作**——是否存在疑似其他线程改动被撤回、覆盖、格式化或顺手重写；冲突文件是否已通过根目录 `mailbox.md` 协商，协商前是否只处理无冲突范围；处理完成的 mailbox 消息是否已删除
18. **简单性审查**——心智模型是否直观；数据流是否短、瘦、单向、可追踪；同一需求是否可用更少状态、模块、转换、缓存、事件或跨层传递实现
19. **对象字段唯一性**——同一对象内是否存在意义完全相同的冗余字段；字段命名、类型、构造点、消费点、fixture 和测试是否收敛到唯一权威字段；是否避免用运行时校验处理编码习惯问题
20. **产物泄露审查**——HTML/Markdown/PDF/报告/页面文案/注释/fixture/snapshot/debug 面板/内嵌 JSON/日志/测试输出是否包含思维链、隐藏推理、scratchpad、提示词片段、系统/开发者指令或模型分析过程；若需要解释，是否已改成可公开的结论和必要理由
21. **测试价值审查**——测试是否保护稳定合同、捕获真实故障、选择最低充分层级、使用正确 mock 边界、由标准 runner 发现，并删除重复或旧测试
22. **测试证据审查**——是否存在源码字符串运行时证明、白盒私有访问、mock 自证、截图即断言、固定 sleep、伪 E2E 或忽略 console/network health
23. **Runner 现代化审查**——是否使用 package 已声明/锁定的现代 runner 或语言标准 runner；是否按主要失败原因拆 case；是否用原生 lifecycle、timeout、mock、隔离和 reporter；是否仍有顶层断言、main 脚本、自建逐文件执行或形式主义语法迁移
24. **Case 独立性审查**——suite/test 是否同步注册，setup/cleanup 是否进入 hook/fixture；是否存在 async suite body、`await test(...)`、自建顺序执行，或 case 依赖兄弟 case 的数据、共享变量修改和执行顺序；按名称过滤任一 case 是否仍能独立成立
25. **开发数据库审查**——数据库测试是否明确复用当前开发数据库，测试数据是否有创建、修改和失败清理责任；是否错误地为每个测试、case 或测试批次新增临时测试库、数据库容器或连接切换

## 流程

1. 读代码变更，按评审范围逐项检查
2. 确认变更覆盖计划大阶段的全部任务；阶段未完成则回 implementation，不评审局部功能点
3. 发现问题后集中修完整阶段内同根因、同模块的相关问题，不运行验收测试
4. 全部问题修完后复评——重新过一遍整阶段评审范围，确认无遗留
5. 整阶段复评通过 → 一次性进入 verification 集中测试
6. 复评不通过 → 继续整批修复，再复评

## 产出

- 复评通过：代码变更 + "评审通过"；涉及测试时附测试价值与入口审查结论
- 复评不通过：回到 implementation，附问题清单
