# product-design

## 最高优先级禁令

以下规则优先于本技能的其他规则，后续条款不得作为例外：

1. **禁止过度锁与并发设计**：没有真实并发入口、共享资源及用户/协议合同，不设计锁、队列、worker、并发池或异步编排。
2. **禁止 smoke/冒烟测试**：服务存活、健康检查、页面可打开或元素存在只能用于环境就绪，不能作为测试或验收证据。
3. **禁止内部防御式编程**：不为理论非法状态增加 optional 分支、默认值、吞错、重复校验、过滤、fallback 或兼容路径；真实 ingress 仅由唯一 owner 处理。
4. **谨慎看待竞态，大部分情况下不可能出现竞态**
5. **不预设边界情况**：没有用户反馈、真实使用证据或既有明确合同，不把想象中的边界情况写成设计、代码、测试或结论；先完成主路径，后续按实际反馈处理。

## 用户体验与心智模型优先

- 需求范围以用户要完成的完整工作流为准，不以“少改文件”或“最小 diff”代替产品判断。
- 当一个交互要跨页面、API、状态、错误反馈、权限或持久化才能闭环时，PRD 必须覆盖完整链路；不得为了缩小改动留下只能展示、不能操作的半成品。
- 优先减少用户需要记忆的状态和步骤，让默认路径可发现、可恢复、可解释；技术实现可以扩大到必要模块，但不得引入无业务价值的复杂度。

## 用户体验目标

- 产品目标始终是让目标用户更顺畅、更有把握地完成任务。UI、交互和功能是实现这一目标的手段，不能各自脱离用户结果单独追求“更丰富”“更炫”或“更多”。
- PRD 必须明确用户当前阻碍、目标任务、成功结果和关键摩擦点；每项 UI、交互或功能要求都要对应至少一个可感知的改善，无法说明改善时不纳入范围。
- 当视觉、交互与功能方案冲突时，以用户能否理解下一步、低成本完成任务并确认结果为准，而不是以实现量、页面复杂度或功能数量为准。

## 复杂度触发的需求回溯

- PRD 要命名核心业务概念、其状态/生命周期和用户可理解的动作结果；不要用含义含混的“处理”“更新”等泛化动作，逼迫 UI 或调用方编排多个底层步骤。
- 若实现反馈某个局部逻辑只能靠大量条件、状态组合或调用顺序才能完成，先回到产品和架构重新审视概念、动作和主路径，不把这类复杂度直接固化为交互、异常提示或验收条件。

## 真实链路优先

- 定义异常、边界条件和验收时，先确认它能否由真实用户流程或真实外部入口产生，并看它经过的上游合同和下游结果；不能从内部函数可被强行传入某值，推导出用户需求或生产风险。
- 用户输入、外部协议、历史数据和第三方数据等真实入口需要明确失败体验；上游合同已排除的理论非法值不写成下游功能、交互或验收要求。局部“更稳”的分支若增加整体心智负担、状态分叉或维护成本，不纳入范围。
- 不把哈希、校验和、指纹或内容比对写成默认的“防错/防重复”验收要求。只有真实安全、协议、内容寻址或幂等合同需要时，才定义用户可感知结果和责任边界。
- 不把锁、后台 worker、队列、并发请求或异步编排当作默认的“更快/更稳”要求；先定义用户是否真的需要同时执行、取消、排队或顺序一致的结果，未形成可观察合同时保持顺序主路径。
- 不把防御式编程写成产品范围：内部前置条件、默认值、额外错误分支和兜底不构成用户功能。只为真实用户或外部入口定义必要的失败体验，并由对应边界统一负责。

## 前置

- 用户提出需求（允许模糊，本阶段负责澄清）
- 涉及新增、修改或迁移测试时，读取并遵守 `test-governance`

## 开发数据库测试约定

- 当前环境的数据库是可任意修改的开发数据库。涉及数据库的验收或测试时，默认复用该库；不得把为每次测试、每个 case 或每个测试批次创建、启动或销毁临时测试库写成需求或验收前提。
- 数据库相关验收只说明需要覆盖的用户结果、业务合同、数据状态和清理要求；具体的数据准备、迁移和清理由 `test-governance` 统一约束。

## 正常功能测试口径

- 正常功能开发后的验收测试只定义为系统测试：用项目已有的 Playwright 测试从 UI 入口完成用户操作，并验证可见结果、状态刷新和失败恢复。
- 系统测试必须联通真实前端、后端和当前开发数据库。验收标准不得要求 unit、component、contract、API 直调、mock、视觉或性能测试，也不得把它们作为替代证据。
- 不定义 smoke/冒烟测试，也不以“页面能打开”“服务可访问”作为功能验收或系统测试的替代证据。

## 状态更新体验

- 需求涉及状态变化、后台任务、消息或协作结果时，PRD 必须定义用户何时、通过何种事件看到更新；优先用户操作响应、服务端推送、订阅或响应式本地状态，而不是定时轮询。
- 只有上游确实没有推送/回调能力时才可接受轮询，并在 PRD 中写明外部限制、用户可见的等待状态、最大等待时间、取消入口和停止条件；不得把持续刷新当作默认交互。

## 断线恢复体验

- 外部运行时、会话或事件流断线时，先在 PRD 标明其权威持久事实源和原生增量游标。上游已有两者时，恢复体验必须是重新连接后从该事实源按游标补读，再继续接收实时更新；不得把中间系统自建事件缓冲、journal、replay 队列、outbox、补偿 watcher 或自动命令重试写成需求。
- 瞬时流式片段和临时进度未被上游持久化时，不承诺断线后逐条补回；恢复后呈现已持久化事实和后续真实更新。上游没有可用的持久事实源或稳定游标时，停止实现并先定义用户可理解的恢复合同，不默认以自建缓冲替代。

## 移动端范围约定

- 用户未明确要求移动端适配、响应式布局或小屏交互时，不把移动端适配列入 PRD、交互定义、验收标准或测试范围；以需求指定的目标平台和视口为准，未指定时按当前桌面目标处理。
- 不因“默认完整性”自行设计移动端页面、断点、触摸交互或小屏专属状态；用户明确提出后再补充对应合同和验收。

## 原型 HTML 复现验收

- UI 复现原型 HTML 时，原型使用的 mock 数据快照是验收基准；验收标准须明确数据版本/来源、字段值与类型、数组顺序、空值/缺失值以及筛选、排序、分页和时间状态。
- 比较原型与目标 UI 前，必须让两者使用同一份或字节等价的 mock 数据，并保持相同视口和交互状态。数据内容不同只能记录为“不可比”，不得据此宣称 UI 100% 一致或把数据差异归因于样式实现；应先对齐数据合同。

## 反模式

1. 禁止不清需求即进入实现——缺关键前提先补证据或问用户，每次最多问一个问题
2. 禁止已载文档/API契约未再确认即改
3. 禁止代码与文档冲突时自行裁决——须报用户确认准绳
4. 禁止UI文案面向开发者/实现——不得出现内部模块名、runtime行为、配置文件名、发布策略、路线图式说明（"当前仅…后续再…"）；占位符、空状态、提示语一律改为用户视角的动作或结果描述
5. 禁止产品决策混入实现细节——本阶段只定义"做什么"和"验收什么"，不定义"怎么做"
6. 禁止用户未要求生成设计稿时强制出设计稿——仅当用户明确要求或改动涉及全新页面/重大交互重设计时方出设计稿
7. 禁止无证据自行设计——先查本仓既有页面、组件、用户反馈和历史决策；只有本地证据不足、用户明确要求或外部事实会改变体验决策时才联网调研同类产品
8. 禁止把实现细节写成验收标准——普通变量名、函数名、文件路径、组件内部结构、私有方法、mock 调用、模板源码片段和局部 CSS 数值不是产品结果；除非其本身是公开格式或设计系统合同
9. 禁止为每个细节机械拆一条测试——验收标准按用户目标、业务规则、状态转移、权限、错误语义和关键风险组织；一条端到端业务结果可以覆盖多个实现细节
10. 禁止把局部理论输入扩张为产品范围——内部调用、强制类型、测试夹具或手工构造才出现的状态，不要求每个下游页面、交互或错误提示分别处理；先确认真实入口和上游合同

## 同类调研

设计功能时先查本仓的既有体验和历史决策；仅在本地证据不足、用户明确要求或外部事实会改变体验决策时，再调研同类产品/同类功能的实现案例：

1. **搜索范围**：开源项目（GitHub）、竞品文档、技术博客、官方文档、社区讨论
2. **搜索关键词**：功能关键词 + 产品/项目名（如 "agent runtime" + codex/hermes/claude code）
3. **调研报告**：每个同类案例记录——产品名、核心功能、交互方式、优缺点、可借鉴点
4. **决策依据**：产品决策必须引用调研报告中的案例，禁止凭空发明

## 产出

PRD，必须含：

- **同类调研报告**：参考的产品案例、交互方式、优缺点、可借鉴点
- **用户体验目标**：用户当前阻碍、目标任务、成功结果、关键摩擦点，以及 UI、交互、功能分别如何改善该结果
- **用户故事**：谁、在什么场景、要达成什么目标
- **交互定义**：关键路径的操作流、状态变化、边界条件
- **验收标准**：每条可判定通过/不通过
- **测试价值口径**：涉及测试时，每条验收标准注明用户可观察结果或稳定业务合同、失败风险与关键路径；不得指定源码字符串、私有实现或 mock 作为通过证据
- **系统测试口径**：正常功能只列 Playwright UI 用户路径及其真实前后端结果；不列其他测试层级或直接接口断言
- **约束说明**：性能、安全、兼容、i18n 等硬约束
